# 服务器编译与运行目录规范

记录日期：2026-10-22。适用于当前开发阶段的服务器构建、启动、打包和本地版本管理。

本规范已在构建脚本中实施。服务器使用固定的产物名称和输出位置，以 Git 管理源码版本；编译产物与默认运行数据集中在 `server/build/`，不混入源码目录。

## 目录约定

以下路径以仓库根目录为基准：

```text
server/
├─ cmd/、internal/                Go 源码
├─ scripts/、tests/               辅助脚本与测试
├─ deploy/                       部署模板
├─ go.mod、go.sum                依赖定义
├─ build.bat                     Windows 编译入口
├─ build.ps1                     测试、检查与实际编译
├─ start.bat                     Windows 启动入口
├─ package-release.ps1           可选的双平台发布打包入口
├─ README.md                     使用说明
└─ build/                        Git 整体忽略，目录按需创建
   ├─ musicserver.exe            Windows amd64 程序
   ├─ musicserver                Linux amd64 程序（可选）
   ├─ data/                      测试数据库、数据库备份、更新暂存
   ├─ media/                     建议放置测试音乐的位置
   ├─ uploads/                   上传确认入库的音频与附件
   ├─ .staging/                  上传暂存
   ├─ packages/                  发布压缩包（可选）
   └─ .server-archive/            历史文件归档（若有）
```

`build/` 同时是产物目录和默认运行目录，**不能按临时编译缓存自动清空**。日常编译只更新目标程序，保留数据库、音乐和其他运行数据。历史归档不参与编译，也不作为源码版本管理的替代方案。

显式指定外部媒体库或数据库路径属于可选覆盖；无参数启动遵循本规范的 `build/` 布局。

## 固定的产物名称

| 用途 | 固定路径 |
| --- | --- |
| Windows 程序 | `server/build/musicserver.exe` |
| Linux 程序 | `server/build/musicserver` |
| Windows 发布包 | `server/build/packages/musicserver-windows-amd64.zip` |
| Linux 发布包 | `server/build/packages/musicserver-linux-amd64.tar.gz` |

程序和压缩包名称不增加版本号、日期、`backup` 或 `validation` 等后缀。同一平台再次构建时更新同一位置的产物。临时验证使用独立的临时目录，不在源码目录旁生成其他程序副本。

源码版本通过 Git 提交区分。程序保留语义版本号，并在启动日志及 `GET /api/v2/health` 中提供：

- `commit`：构建时对应的 Git 提交号。
- `modified`：构建时仓库是否存在未提交修改。

构建使用 `-trimpath -buildvcs=auto`。没有可用 Git 构建信息时，提交号显示为 `unknown`。这些字段记录的是构建时状态，提交新的源码后不会自动改变已编译程序的信息。

## 日常编译与启动

以下命令在 Windows 的仓库根目录执行：

```bat
cd server
call build.bat
call start.bat
```

编译前先停止运行中的服务器。脚本检测到目标 `build/musicserver.exe` 正在运行时会拒绝构建，并提示先停服。

`build.bat` 调用 `build.ps1`，依次执行：

1. `go test ./... -count=1 -timeout 120s`。
2. `go vet ./...`。
3. 编译到固定目标路径。

任一步失败就停止，返回非零状态；构建成功明确输出 `BUILD SUCCEEDED` 和完整产物路径，构建失败输出 `BUILD FAILED`。Windows 产物固定为 amd64，使用 `CGO_ENABLED=0`。脚本设置的 Go 环境变量在结束时恢复，不永久修改系统配置。

脚本会查找已有 Go 工具链；需要指定安装位置时，可在 `server` 目录执行：

```bat
call build.bat -GoRoot "C:\Program Files\Go"
```

`start.bat` 固定运行脚本旁 `build/musicserver.exe`，不会回退使用源码目录中的旧程序。从其他工作目录调用编译或启动脚本，也使用同一产物位置。

默认监听 `127.0.0.1:8080`。首次运行在真实终端中隐藏输入并确认 `admin` 密码；后续运行直接启动，不需要显式传入数据库路径、媒体路径或用户名。不设置默认密码，也不把密码、API Key 写入启动脚本。

## 路径与音乐扫描

默认媒体根目录为程序所在目录，即 `server/build/`；建议把测试音乐放入其下的 `media/`。数据库默认位于 `build/data/library-v4.sqlite`。相对路径参数也以程序所在目录为基准，不随终端当前目录改变。

这里有两个不同范围的排除规则：

| 规则 | 范围与作用 |
| --- | --- |
| Git 忽略 | 整个 `server/build/` 不进入 Git，包括程序、数据库、音乐、暂存、发布包及归档 |
| 音乐扫描跳过 | 扫描媒体根目录时，跳过数据库目录、`.staging` 和 `.server-archive`，防止内部文件被识别为正式曲目 |

默认不会扫描 `server/cmd/`、`server/internal/` 等源码目录。曲目路径相对于媒体根目录保存；同一数据格式下，停服后整体移动 `build/`，可直接运行其中的程序继续使用，无需携带源码。显式配置的外部绝对路径需要另行保留或调整。

## Linux 编译与发布打包

当前脚本在 Windows 上执行测试和检查，再交叉编译 Linux amd64。只需要 Linux 程序时，在 `server` 目录执行：

```bat
call build.bat -Target linux
```

该操作生成 `build/musicserver`，不会把 Linux 程序命名为 `.exe`。它不会验证程序在 Linux 主机上的实际运行行为。

需要两个平台的发布包时，在 `server` 目录执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\package-release.ps1
```

打包脚本复用统一构建入口，生成两种固定名称的程序，再将压缩包写入 `build/packages/`。Windows 包仅包含 `musicserver.exe` 和 README；Linux 包另包含部署模板。打包使用明确的文件清单，不包含数据库、媒体、密码、运行配置或暂存文件。

## Git 提交与版本核对

- 每次完成升级或修复并通过相应验证后，创建 Git 本地提交。
- 只提交本次任务相关源码、脚本、文档和测试；不提交 `build/` 或其他密钥、数据库、媒体、日志与归档。
- 未经用户要求，不推送远程仓库。
- 需要回退程序时，选择对应源码提交重新编译，产物路径和名称保持不变。

需要让最终产物明确对应已提交版本时，先完成代码验证和本地提交，再从干净的工作区重新构建；启动后核对健康检查的 `commit` 与预期提交一致，`modified=false`。已经在提交前编译的程序不会因为随后执行了 `git commit` 就自动更新构建标识。

## 开发阶段的数据处理

当前服务器数据仅用于测试，升级不提供旧数据格式的兼容或自动迁移。格式不匹配时使用新的测试数据库重新初始化，不在构建脚本中加入旧库转换逻辑。

普通编译不删除数据。需要重置测试库时，先停服，再清理 `build/data/`，下次启动重新设置管理员密码并扫描媒体。重置后旧 UUID、歌单、人工修改和账号不会保留；只保留音频文件不能恢复这些数据库信息。
