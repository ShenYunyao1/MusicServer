# 数据库保留升级与验收

日期：2026-10-28，2026-10-29 更新正式发行验收。对应标签系统 P06；用户已明确要求兼容现有数据，并授权推送、测试通过后发行。0.20.3／schema 7 桥接版及 0.21.1／schema 8 标签版均已正式发行。按用户最新要求，不再关注云端，实际安装及 root 更新器维护由用户按发行说明执行。

## 采用的方案

保留现有数据库并执行版本化事务迁移，不删除旧库、不重新创建账户、不重新导入音频。当前明确支持的跨格式路径是 schema 7 → 8；未知、缺少版本或反向路径拒绝。新增版本必须编写对应迁移和验证，不能只改版本号让旧库“通过”。

迁移只新增标签、来源、任务与保存条件等表及索引，原有行不反序列化重建。曲目 UUID、路径、音频摘要、原始上传者、密码哈希、Key／授权／统计、歌单顺序和备注、公开／共享关系、邀请／订阅、邮箱资格、配额及设置保留。正常服务器重启仍撤销旧网页会话，需要重新登录；这是既有安全行为，不会删除密码或 Key。

旧 `genre` 继续保留。重新扫描媒体属于可选的标签归一整理，沿用既有 UUID，并保留人工确认／忽略；不承担数据库升级职责。原始文件重新导入无法可靠还原账户、授权及私有歌单，所以不作为升级主方案。

## 迁移前保护

正常启动即将跨 schema 时，先验证双格式标记、SQLite 完整性和外键关系，再按数据库／WAL 大小、额外迁移余量和已有磁盘预留设置检查空间。校验或空间不足立即失败，不执行迁移。

通过 SQLite 一致性快照生成旧格式库，位于数据库同目录：

```text
.schema-7-to-8-随机目录/snapshot.sqlite
```

Linux 目录为 0700、文件为 0600；快照重新检查格式、完整性、外键并刷盘，成功后才进入事务迁移。原库与快照均保留；迁移失败重试创建新的独立快照，不拿可能过时的文件覆盖本次恢复点。已有 schema 8 重启不再生成重复快照；空新库直接初始化目标格式，不触发旧数据迁移快照。历史 schema 7 桥接程序启动同格式库也不触发跨版本备份。

这里是数据库迁移快照，不包含音频。音频不被这次迁移改写；日常灾备继续使用网页完整备份。迁移快照不会自动删除，后续确认升级稳定并另有有效备份后再由管理员整理。直接手工更换程序也执行同一前置保护。

## 网页更新与回退

完整命令见随包分发的 [手动升级指南](../server/deploy/schema8-upgrade.md)，维护边界见 [独立更新器维护与桥接](../server/deploy/updater-maintenance.md)。用户按以下顺序操作：

1. 保存完整备份，安装已发布的 0.20.3／schema 7 桥接主程序；latest 已前进时使用指南中的固定版本排队步骤。
2. 使用已验签的 0.20.3 正式包维护 root 独立更新器，并核验能力文件；不能只更新普通主程序便宣称跨 schema 更新已可用。
3. 在网页检查并安装已通过全部门禁的 0.21.1／schema 8。更新器停服，核验并备份源格式库，再切换程序；新程序执行迁移。
4. 健康检查失败或更新中断时，更新器恢复与旧程序匹配的源库快照和程序，再启动旧版；旧程序不能直接读取新格式库。

更新器侧也增加了外键检查，防止只通过 `integrity_check` 的关系损坏库被当成可用升级／回退快照。

手工恢复必须先停止相关程序，保留故障现场，并使用匹配的旧程序和迁移前快照恢复，不直接改 `PRAGMA user_version`、不把旧／新库合并。迁移前快照只包含当时数据，后续新增数据需要另行保全，不能把恢复旧快照等同于无损降级。
