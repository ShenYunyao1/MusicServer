## 二、需展开的条目

### B-36（P1）暂存字节有界，但仍不并入账户配额

- 新机制：写盘前 `reserveTemporaryUpload`（`staging.go:184-188`）、元数据事务内复核（`staging.go:281-291`、`upload_budget.go:185-214`），账户 2 GiB / 全站 16 GiB / 16·256 任务，默认值见 `upload_budget.go:21-23`。
- 未闭合部分：
  1. `accountUsage` 仍只统计 `tracks`（`storage.go:165-194`），`checkAccountQuota` 只在 commit（`staging.go:586`）：**已入库 + 暂存** 合计不受账户配额约束。
  2. `upload_budget.go:52-55`：有配额账户的临时上限是 `max(2×MaxUploadBytes, LimitBytes)`，最低仍为 1 GiB（默认 `MaxUploadBytes=512 MiB`）。100 MiB 配额账户可暂存 1 GiB。
  3. 1 GiB 封面预算仍只在提交时统计（`cover_store.go:202-242`），暂存内的 base64 封面改由 64 MiB 元数据预算兜底，口径不同。
- 风险量级：8 个合格账户即可把 `.staging` 推到全站 16 GiB 上限并拒绝全站上传；单账户 2 GiB。TTL 30 分钟 + 每分钟清理兜底。
- 判定：**部分修复**。P1 的「不可回落增长」已收敛为「有界占用」，但「按配额收紧」未成立。

### B-40（P2）封面鉴权改成 SQL 全表扫描

- 现状：`coverReadable` 用 `SELECT EXISTS(... json_extract(t.payload,'$.cover_id')=@cover ...)`（`cover_access.go:47`）判定可见性，在 `readSnapshot` 内执行，不再把全库读进 Go 内存、不再持 `writeMu`。
- 残留：`json_extract(payload,'$.cover_id')` **没有表达式索引**（全部 `CREATE INDEX` 见 `sqlite.go:25-43`，无 payload 表达式索引），每次封面请求都要扫 `tracks` 全表并解析每行 payload（含歌词）。
- 影响：封面网格首屏几十张封面 = 几十次全表解析；`SetMaxOpenConns(1)` 下这些扫描独占唯一连接，等同于把原来的「读锁内全量解码」换成「SQLite 内全量解析」，成本量级未变。
- 建议：schema 10 把 `cover_id` 落列并建索引，或建 `(cover_id, playlist_id)` 引用表；过渡期可先给 `EXISTS` 加 `LIMIT 1`（`EXISTS` 已隐式短路，但无索引仍要扫到命中）。
- 判定：**部分修复**，残余升级为 B-88。

### B-92（P3）finish 转暂存的「双计费」会让合法上传在最后一步 429

### B-104（P3）切歌无条件递增详情世代，会静默取消在途的详情打开

- 位置：`online-player.js:70`、`library.js:65-69`。
- 证据：`playOnlineTrack` 每次点击/自动接续都执行 `state.trackDetailGeneration=(state.trackDetailGeneration||0)+1`；曲目详情入口用同一个 `trackDetailGeneration` 做守卫，响应回来若世代已变就直接丢弃（不弹窗、不报错）。
- 影响：慢网络下点开详情，恰逢自动接续/队列切歌，用户感知为「点了没反应」；与 B-47 的「防旧响应覆盖」目的无关，属误伤。
- 建议：详情与播放使用独立世代（`detailGeneration` / `playbackGeneration`），只在显式打开详情时递增详情世代。
- 置信度：高（静态）。

### B-105（P3，回归）账户基线不含「他人公开且未订阅」的歌单，播放队列跨页修订漏检

- 位置：`browse_revision.go:25`、`browse.go:140-141`、`browsePlaylistTracks`（`browse.go:415-440`）、`online-player.js:127-133`。
- 证据：基线里的歌单集合是 `p.owner_id=? OR 已订阅 OR role='admin'`；而 `source=public` 的播放只要求 `publishedPlaylist`，**不要求订阅**。他人增删曲目或重排该公开歌单时，账户基线不变，逐页 `offset` 拉取不会拿到 409 `BROWSE_RESTART`；浏览器端逐页比对 `revision` 因此不会重试。
- 影响：跨页构建队列时可能跳过或重复曲目，且无任何提示。基线（全局 `meta.revision`）下这类改动会改变修订号、能触发重试——属 B-69 方案引入的漏检。
- 建议：playback 请求把目标歌单的 `version`/可见状态并入校验，或队列改用游标/服务端快照而非 `offset` 分页。
- 置信度：高（代码路径可证；实际丢曲取决于并发编辑窗口）。

### 7.2 新增发现（B-106～B-140）

以下 35 条为本轮复核中新写入清单的问题：B-134 为 P2 回归（订阅详情搜索后实时通道失效），其余均为 P3；B-106/B-110/B-113/B-115/B-126 属基线既有的性能与统计口径类，其余由本轮修复、新增机制或四个切片的交叉核对带出。B-112～B-140 的触发与影响经源码回读确认，量级未实测。

- **B-106（P3）只读池未覆盖的读路径仍直连唯一写连接**：`readDatabase()` 只服务迁移过的浏览/公开/订阅/词典/常听路径，其余读处理器仍用 `a.store.db`/`store.db` 直查，例如普通歌单详情逐曲目 `readTrackFrom(a.store.db, …)`（`server.go:1002-1009`）、每请求 Key 认证 `currentKeyAuth(store.db, …)`（`server.go:793-816`）、会话校验与标签 schema 探测（`auth_http.go:178`、`tag_*_http.go`）。WAL 已让写连接不再被长读快照独占，但这些读仍与写事务争用单连接。属基线既有，非本轮回归。
- **B-107（P3）公共词典上限计入永久不可回收的合并墓碑**：合并把源行置 `deleted=1, merged_into=<目标>`（`track_tag_merge.go:210-216`），而回收要求 `merged_into IS NULL` 且无子行引用（`tag_contribution_budget.go:62-67`），创建上限却统计 `count(*) FROM tags WHERE scope_id=?`（`tag_dictionary.go:448`）。长期合并会把名额永久占掉，触顶后成员创建被拒且无回收路径（管理员也不能删已删词条）。为 B-91 修复的副作用，量级取决于合并频次。
- **B-108（P3）WAL 成为启动硬依赖**：`initializeReadPool` 设置 `journal_mode=WAL` 后校验必须为 `wal`，否则关闭数据库并拒绝启动（`read_snapshot.go`、`store.go:111-114`）。在 WAL 不可用的介质（部分网络盘、只读/受限文件系统）上，此前可用的单连接 rollback journal 模式现在直接起不来；同时 WAL 文件（`-wal`/`-shm`）也进入备份大小估算与残留清理视野（`admin.go:47`、`backup_bundle.go:194`）。
- **B-109（P3）`/api/v2/setup` 的 405 仍不带 `Allow`**：`setup.go:79` 直接 `writeError(405, "method not allowed")`，未走 `methodNotAllowed`；该端点实际允许 `GET, POST`。B-55/B-99 的集中表未覆盖这条唯一残留。
- **B-110（P3）配额账户的上传提交仍在写事务内做全库统计**：`checkAccountQuota` 解码全部 `tracks.payload` 并对每个路径 `Stat`（`storage.go:165-210`），由提交路径在写锁内调用（`staging.go:589`）。仅对 `LimitBytes > 0` 的账户生效（`:200-202` 早退），但大会库下每次提交都是 O(库) I/O + 全表解码，属基线既有。
- **B-111（P3）删除账户残留浏览计数键**：`PurgeUser` 清理会话、订阅、邀请、续传、邮件、配额等（`permanent_delete.go:288`），未删 `meta` 中 `browse/account/<id>`；每删除一个账户残留一行常量计数，只增不减（无功能影响）。
- **B-112（P3，回归）30 分钟上传期限到点返回 400 而非 408，前端不重试**：`progressBody` 到点返回 `os.ErrDeadlineExceeded`（`request_limits.go:53-56`），而 408 分支只匹配 `context.DeadlineExceeded/Canceled`（`upload_resume.go:695-698`），两者不是同一 sentinel → 落入 default 400 `UPLOAD_INVALID`；`writeUploadBodyError` 只特判 `MaxBytesError`（`storage_http.go:38-48`），前端仅对 408/429/5xx 重试（`upload-resume.js:361`）。影响：合法慢速上传在 30 分钟处失败且文案为「无效上传」，用户与日志均归因错误；PATCH 可查 offset 续传，但需人工重试。建议两处加 `errors.Is(err, os.ErrDeadlineExceeded)`（或 `net.Error.Timeout()`）→ 408 `UPLOAD_INTERRUPTED`。置信度高。
- **B-113（P3）上传准入在 `tempMu` 内遍历 `.staging` 并逐条 stat 该账户已入库文件**：`reserveTemporaryUpload` 全程持 `tempMu`（`upload_budget.go:51-53`），先 `directoryBytes(.staging)`（`:55`），再 `accountUsageForIDs` 对每个 `tracks.path` 调 `root.Stat`（`:149-156`、`account_storage.go:29-79`）。影响：每次暂存/续传创建/晋升准入都是 O(曲目数) 次 stat 且全站串行，大库上传延迟上升；正确性不受影响。建议维护持久化 `used_bytes` 或改用 `SELECT sum` 聚合，目录字节改增量计数。置信度高，量级待实测。
- **B-114（P3）硬链接晋升窗口内 `.staging` 字节被重复计数，可能误报 429**：`directoryBytes` 按路径累加（`storage.go:215-236`），晋升先 `root.Link`（`upload_pipeline.go:86`）且成功后才删 `.part`（`upload_resume.go:613-617`），同一 inode 短暂出现两个名字；`charges` 去重只作用于 `own/size`，不作用于 `global`。影响：全局暂存接近上限时物理未增却可能 429 `UPLOAD_TEMPORARY_LIMIT`。建议按 `(dev,inode)` 去重或对同 id 的 `.part`+staging 只计一次。置信度中高。

- **B-133（P3）邮件 secret 崩溃孤儿与旧文件删除失败仅记日志**：新 secret 在写事务外先写（`mail_settings.go:369-372`），清理依赖进程正常返回；在写入与提交之间崩溃会留下无引用的明文凭据且无启动清理；提交后旧 secret 删除失败只发 `mail.failed`（`:411-416`）。影响：`.mail-secrets` 累积无引用 SMTP 密码（受 0600/DACL 保护），旧凭据残留。建议启动清理未被 `secret_id` 引用的文件、删除失败升级为告警。置信度高。

- **B-135（P3）浏览/搜索/索引 DDL 未版本化，`IF NOT EXISTS` 使后续修正对老库永不生效**：建表、触发器、封面表达式索引、审计部分索引全部 `IF NOT EXISTS`（`browse_indexes.go:20,33-41,53-80`），`browse/search_version` 只保护 `browse_track_search` 回填，`schema_migrations.go` 的 7→8/8→9 也无对应项。影响：将来修正触发器体或索引表达式后，老库继续使用旧定义且无告警，与「性能结构可重建」的声明不符。建议增加 `browse/schema_version`，按版本 DROP/CREATE 并补一致性测试。置信度高。
- **B-136（P3）首启/升级的回填与建索引是硬失败点，坏 JSON/权限错误直接起不来，离线 CLI 也会写库**：回填与表达式索引直接对 `tracks.payload` 求 `json_extract`（`browse_indexes.go:29,38-40`），任一失败 → `loadSQLiteForTarget` 返回错误 → `log.Fatal`（`sqlite.go:130-134`、`store.go:102-107`）；`NewOfflineStore` 走同一路径（`admin.go:64`），把「离线管理」变成写操作。影响：旧库有一行坏 `payload`、目录只读或大库首次升级都会失败/长时间不可用，且离线 CLI 可能与在线写并发。建议回填加 `json_valid`/逐行容错、分批可续、离线 Store 跳过写型初始化。置信度中高。
- **B-137（P3）账户修订把标签 scope 并入所有浏览页，标签写入让打开的浏览页 409**：`browseAccountRevision` 固定 `includeTags=true`（`browse_revision.go:54-80`），所有浏览页都用它，但浏览投影本身不含 `tag_summary`（`browse.go:357-376,486-506`）。影响：任何打标/改名/合并都会改变浏览修订，翻页/刷新 409 并重取；标签批量导入时放大明显。建议浏览页改用 `includeTags=false`，标签/筛选视图保留带 tags 的基线（`track_filters.go:371-383` 已是这种分离）。置信度中高。
- **B-138（P3）4 条只读连接成为新的共享瓶颈，调用方普遍 `context.Background()` 不可取消**：读池容量 4（`read_snapshot.go:43-44`），而公开详情、订阅实时、标签读等多处用 `context.Background()`（`community_http.go:44`、`community_realtime.go:191,246`、`community.go:256`、`tag_dictionary.go:19-26`）；每次写提交都会让 128 路 SSE 同醒重算（`community_events.go:75,94,20`）。影响：交互读（浏览/常听/标签）在池上排队且无排队超时，客户端断开也不释放；这是 WAL 之外的新瓶颈（与 C-25 相关）。建议读 ctx 从 request 派生并设单查询超时、同一实时视图多路共享一次计算。置信度中。
- **B-139（P3，B-86 残余）管理员自有歌单/播放仍整段写事务，审计写入还会唤醒全站 SSE**：`browse.go:108-110` 对 admin 的 `playback?source=own` 与所有 `playlists/<id>` 详情改走 `a.store.transaction`，而审计只在「非本人且非系统」时写（`:157-170`）——管理员读自己的资源也持写锁、无审计；写事务提交后的 stamp 含 `MAX(audit)`（`sqlite.go:327`、`community_events.go:20`），管理员翻页产生的审计行会推高 stamp → 全部实时流重算。建议读始终走只读快照、审计改为读完后独立短写事务、实时 stamp 不依赖 `MAX(audit)`。置信度高。
- **B-140（P3，B-74 残余）已计数会话占满 3000 后最坏 24 小时 429，`media:read` Key 约 25 分钟即可占满**：回收只针对 `counted=0 AND last_seen_at < now-1min`（`listening.go:202-217`），已计数会话仅按 `started_at < now-24h` 自然过期（`:189-190`）；持有 `media:read` 的 Key 可每分钟建 120 个新会话并在 30 秒后合法计数。影响：写脚本或异常客户端可在约 25 分钟内把本账户推到 24 小时 429，前端只显示「稍后重试」。建议对会话创建加账户级速率/并发上限，或对 counted 会话提供按 last_seen 的淘汰策略。置信度中高。

### 7.3 新增边界

- **C-24（平台边界）WAL 与备份/恢复语义**：数据库固定 WAL 后，热备走 `VACUUM INTO`（`admin.go:47-90`）保证一致快照，空间估算计入 `-wal`；归档内的 `database.sqlite` 为快照文件而非裸拷贝。介质不支持 WAL 时的降级路径**不存在**（见 B-108），需产品明确「仅支持本地/可写文件系统」。
