## 二、需展开的条目

### B-36（P1）暂存字节有界，但仍不并入账户配额

- 新机制：写盘前 `reserveTemporaryUpload`（`staging.go:184-188`）、元数据事务内复核（`staging.go:281-291`、`upload_budget.go:185-214`），账户 2 GiB / 全站 16 GiB / 16·256 任务，默认值见 `upload_budget.go:21-23`。
- 未闭合部分：
  1. `accountUsage` 仍只统计 `tracks`（`storage.go:165-194`），`checkAccountQuota` 只在 commit（`staging.go:586`）：**已入库 + 暂存** 合计不受账户配额约束。
  2. `upload_budget.go:52-55`：有配额账户的临时上限是 `max(2×MaxUploadBytes, LimitBytes)`，最低仍为 1 GiB（默认 `MaxUploadBytes=512 MiB`）。100 MiB 配额账户可暂存 1 GiB。
  3. 1 GiB 封面预算仍只在提交时统计（`cover_store.go:202-242`），暂存内的 base64 封面改由 64 MiB 元数据预算兜底，口径不同。
- 风险量级：8 个合格账户即可把 `.staging` 推到全站 16 GiB 上限并拒绝全站上传；单账户 2 GiB。TTL 30 分钟 + 每分钟清理兜底。
- 判定：**部分修复**。P1 的「不可回落增长」已收敛为「有界占用」，但「按配额收紧」未成立。

### B-40（P2）封面鉴权改成 SQL 全表扫描

- 现状：`coverReadable` 用 `SELECT EXISTS(... json_extract(t.payload,'$.cover_id')=@cover ...)`（`cover_access.go:47`）判定可见性，在 `readSnapshot` 内执行，不再把全库读进 Go 内存、不再持 `writeMu`。
- 残留：`json_extract(payload,'$.cover_id')` **没有表达式索引**（全部 `CREATE INDEX` 见 `sqlite.go:25-43`，无 payload 表达式索引），每次封面请求都要扫 `tracks` 全表并解析每行 payload（含歌词）。
- 影响：封面网格首屏几十张封面 = 几十次全表解析；`SetMaxOpenConns(1)` 下这些扫描独占唯一连接，等同于把原来的「读锁内全量解码」换成「SQLite 内全量解析」，成本量级未变。
- 建议：schema 10 把 `cover_id` 落列并建索引，或建 `(cover_id, playlist_id)` 引用表；过渡期可先给 `EXISTS` 加 `LIMIT 1`（`EXISTS` 已隐式短路，但无索引仍要扫到命中）。
- 判定：**部分修复**，残余升级为 B-88。

### B-41（P2）订阅详情的实时投影仍在写锁内逐曲目

- 已修：`/api/v2/public/...` 详情走分页（`public_detail_page.go`），实时投影的公开详情分支用 `readSnapshot`（`community_realtime.go:245-261`）。
- 未修：`community_realtime.go:181-201` 的 `view.SubscriptionDetail` 分支仍 `s.transaction` + `for _, id := range p.TrackIDs { readTrackFrom(tx, id, true) }`：持全局 `writeMu`、逐曲目反序列化含歌词 payload，且无条数上限（`subscriptionView` 返回全量 `TrackIDs`）。
- 影响：订阅一个大歌单（数千首）后，任何社区变更触发的实时快照重算都会长时间占住写锁，与 B-86 同属「读路径塞进写事务」。
- 建议：改用 `readSnapshot` + 分页/上限，或按 `playlist_tracks` 一次 JOIN 投影。
- 判定：**部分修复**，残余升级为 B-89。

### B-44（P2）公共词条治理的残留

- 已实现：同事务预算（每小时 20、24 小时 100，管理员豁免），公共 scope 满 10000 时压缩墓碑（单次 1000）。
- 残留：
  1. 预算检查（`tag_dictionary.go:432-436`）在墓碑回收（`:445-457`）之前：全员触顶时会先 429，普通成员永远无法触发回收，只能等额度恢复或管理员操作。

  3. 预算依赖 `audit` 行，未发现 `DELETE FROM audit` 裁剪路径，行数单调增长（长期）。
- 判定：**部分修复**，剩余属产品裁定（C-21）。

## 三、新发现（本轮修复引入或新暴露）

### B-86（P2）浏览/标签同步的「账户可见性指纹」改为全库哈希，并在写锁事务内执行

- 位置：`browse_revision.go:11-77`；调用点 `browse.go:105-115`、`:189-196`、`track_filters.go:368-378`、`tag_sync.go:16-23`、`tag_facets.go:53`、`track_filter_batches.go:12`。

- 置信度：高（锁与路径直读；耗时未实测）。

### B-87（P2）上传读期限按每次 Read 续期且无总时长上限，可滴流长期占用全站上传名额

- 位置：`request_limits.go:35-43`、`server.go:87-107`；名额 `request_limits.go:56-83`。
- 证据：`progressBody.Read` 每次读都把读期限重置为 `now+2min`（`:40-43`）；上传名额为每账户 2、全站 16（`:63`、`:72-81`），且 `staging.go:184` 在读数前就按 `temporaryReaderBound` 预留字节。

- 置信度：高（代码路径直读；未实测滴流）。

### B-88（P2）封面鉴权全表 `json_extract` 扫描且无索引

### B-89（P2）订阅详情实时投影在写事务内逐曲目解析全量 payload

### B-90（P3）`GET /` 每次读两条 SQL，首页与写负载耦合

- 位置：`server.go:160-167`、`listening.go:83-86`、`schema_migrations.go:23-39`。
- 证据：首页/登录页每次请求执行 `PRAGMA user_version` + `SELECT value FROM meta`，在 `SetMaxOpenConns(1)` 下排在长写事务之后；改动前首页不碰数据库。
- 影响：扫描/批量标签写入/长事务期间，登录页与首页可能等待数秒；读失败按禁用处理（fail-closed），不会给出错误页面。

### B-91（P3）墓碑压缩会删除「合并源」，保存筛选丢失重定向且错误语义不一致

- 位置：`tag_contribution_budget.go:30-37`、`tag_dictionary.go:445-457`、`track_filters.go:97-130`、`saved_track_filters.go:63-78`、`browse.go:291-301`。
- 证据：压缩条件不排除 `merged_into` 指向它的合并源；`resolveFilterTag` 只在 `hop>0` 时把「读不到」翻成 `errFilterReference`（`:107-113`），首跳直接返回 `errResourceHidden` → 应用筛选按 404 `NOT_FOUND`；同一引用在保存筛选校验接口报 `FILTER_REFERENCE_INVALID`。
- 影响：原本能经 `TagRedirect` 自动跳转的筛选永久失效；两个接口对同一失效给出不同语义。
- 建议：压缩时排除被保存筛选引用或作为合并源的墓碑，或保留轻量 `id→merged_into` 重定向表；首跳错误也归一为 `errFilterReference`。
- 置信度：中高（需词典满额触发）。

### B-92（P3）finish 转暂存的「双计费」会让合法上传在最后一步 429

- 位置：`upload_budget.go:152`、`staging.go:184`、`upload_resume.go:552-598`。
- 证据：默认 `OwnerBytes=2 GiB`、单文件上限 512 MiB。顺序上传 4 个 512 MiB 文件时，前 3 个已转暂存（1.5 GiB），第 4 个创建时 `1.5 GiB > 2 GiB − 512 MiB` 为假 → 准入；finish 时 `.part` 与目标暂存名同时计费（`own=2.0 GiB > 1.5 GiB`）→ 429。一般条件 `other + 2S > OwnerBytes`。
- 影响：上传最后一步失败，提示「临时空间上限」而非「请先入库/取消待确认预览」；需先清理其他预览再重试。
- 建议：finish 只补差 `max(0, S − pendingCharge)`，或创建时预留转暂存余量。
- 置信度：高（算术可静态推导）。

### B-93（P3）finish 的 3 秒冷却与前端 2.1 秒重试预算冲突，真实原因被遮蔽

- 位置：`upload_resume_verification.go:12-47`、`upload_resume.go:560-563`、`upload-resume.js:289-301`。
- 证据：准入先置 `now+3s`，任意失败再由 `defer` 重置为「结束+3s」；前端把 429 当可重试，按 300/600/1200 ms 重试后抛最后一次错误。
- 影响：首次因空间/存储不足失败时，用户看到「校验失败，请等待 3 秒」，等 3 秒后仍失败，误判为校验损坏。
- 建议：只在 `errResumeCorrupt` 等校验类错误置冷却；`Retry-After` 与冷却一致并保留原始原因。
- 置信度：中高（静态；该失败路径必然发生）。

### B-94（P3）一条格式异常的 `upload_resume/*` 元数据会阻断全站上传

- 位置：`upload_budget.go:92-106`；对照清理路径 `upload_resume.go:945-947`。
- 证据：预算扫描对非 `upload_resume/<32 hex>` 或 `size` 非整数的行直接返回 `errResumeCorrupt`，而清理只按 TTL 删除合法键，该行永不被清理。
- 影响：stage/create/patch 全路径失败，全站上传不可用，需人工修库。正常代码不写这种行（可达性低）。
- 建议：预算扫描跳过非法行并单独上报管理员，不用全局错误阻断所有租户。
- 置信度：高（静态）。

### B-95（P3）公共词条预算的 `Retry-After` 固定 3600，与 24 小时上限冲突

- 位置：`track_tags_http.go:65-70`、`tag_contribution_budget.go:13-26`。
- 证据：同一错误同时表示「1 小时 20 个」与「24 小时 100 个」，响应一律 `Retry-After: 3600`。
- 影响：命中 24 小时上限后按提示重试仍 429，客户端退避失效且无法得知真实可用时间。
- 建议：把命中的窗口与最早可用时间编码进错误，`Retry-After` 用真实剩余秒数。
- 置信度：高。

### B-96（P3）已入库且原目标未知的行，「改为当前目标并重试」无效

### B-97（P3）`BACKUP_BUSY` 把「另一个永久删除」也当作备份冲突

### B-98（P3）恢复残留目录与锁文件只在「同目标下次恢复」时清理

### B-99（P3）405 的 `Allow` 覆盖仍不全

### B-101（P3）每个上传 PATCH 都在 `tempMu` 内做全目录遍历 + 两张表全量扫描
