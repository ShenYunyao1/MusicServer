## 二、新增发现（B-148～B-154）

### B-148（P2）媒体扫描对每个未变化曲目重算存储引用，全库扫描退化为 O(N²) 并放大写事务

- 位置：`scan.go:375`（整次扫描单事务）、`:380-480`（逐候选）、`:472-476`（无条件调用）；`storage_projection.go:63-99`（`replaceStorageRefs` 每次两次账户聚合并 DELETE/INSERT）、`:101-109`（`writeTrackStorage`）。
- 证据：`writeTrack` 已在元数据/标签变化时写过引用（`scan.go:439`、`:457`），随后 `:474` 对同一曲目**再写一次**；对未变化曲目则**只**由 `:474` 写入。每次调用执行 `accountStorageBreakdown` 两次，其 SQL 为 `SELECT ... FROM browse_storage_refs WHERE owner=? AND resource_type<>'stage' GROUP BY asset,kind`（`storage_projection.go:60`），按 `browse_storage_owner(owner,asset,kind,bytes)` 索引扫描该账户全部引用。单账户曲目数为 N 时，每条曲目约 3 条引用，N 次调用 ≈ 2×3N² 次索引访问，另有 N 次 DELETE+N 次 INSERT 写放大。
- 触发：管理员「媒体扫描」固定全量（`scan.go:189-206`），扫描所有曲目（含未变化项）。
- 影响：大库（数万曲目）扫描耗时按平方增长，普通刷新容量不再触发扫描，但维护扫描仍是唯一的大小校正入口；扫描全程持有唯一写连接，期间上传提交、编辑、删除、实时审计写入被阻塞，WAL 显著增长；取消或失败会整体回滚、下次重跑同样慢。
- 修复建议：仅在「观测 size 与现有投影不一致」时更新（先读该曲目引用/大小比较，相等即跳过）；变化曲目复用 `writeTrack` 已完成的一次写入，避免二次 `writeTrackStorage`；账户聚合改为按曲目资产增量调整（引用表本身已按资产去重），不要每条曲目重算全账户。
- 置信度：高（静态复杂度可证；未运行实测）。

### B-149（P2）扫描校正触发配额拒绝，已超额账户会让整次扫描失败并回滚

- 位置：`scan.go:474` → `storage_projection.go:101-109`（`enforce=true`）→ `:84-97`（`after.total() > before.total()` 且超过 `LimitBytes` 返回 `errStorageQuota`）。
- 证据：扫描观察到文件增大（外部替换、旧投影被校正为真实大小）时 `after > before`，若该账户已超过配额则整条语句返回 `errStorageQuota`；错误从 `:474` 冒泡到扫描事务 `:375`，整个扫描回滚，`:514-521` 的 `storage_refreshed_at` 也不会写入。
- 触发：项目明确「存量超额数据保留」（`server/deploy/release-notes.md`），因此存在已超额账户；扫描任意一次向上校正即触发。
- 影响：媒体扫描反复失败、引用永不校正，管理员必须先调高配额才能扫描；失败信息只是 `errStorageQuota`，与「扫描」语义不符，易被误判为数据库故障。
- 修复建议：扫描/维护校正使用不拒绝的写入（例如 `enforce=false` 或仅记录 `over_quota` 告警并照常更新引用），配额拒绝只保留在用户写入路径；如需审计，单独记录超额事件。
- 置信度：高（路径确定，触发条件明确）。

### B-150（P2）续传清理把临时读取错误当作「已过期」，会删除在途 `.part` 与检查点

- 位置：`upload_resume.go:948-1036`（`cleanupResumableUploads`），关键判定在 `:992-1001`；`readResume` 对非 `ErrNoRows` 的数据库错误原样返回（`:157-170`）。
- 证据：`task, e := readResume(s.db, id)`；`expired := e != nil || !time.Now().Before(task.ExpiresAt)`。当 `e` 是 `sql.ErrConnDone`、busy 超时等**临时**错误时仍进入过期分支：`e == nil` 为假跳过 stage 清理，随后无条件 `root.Remove(resumeFilePath(id))` 删除 `.part`，移除成功即 `DELETE FROM meta` 删除检查点（`:1007-1016`）。`readUser` 读取失败同样被当作过期（`:995-996`）。
- 触发：清理周期（启动/定时，`server/cmd/musicserver/main.go:100`）、账户删除（`permanent_delete.go:232`）与数据库关闭/忙/连接断裂并发；概率低但并非不可达。
- 影响：在途上传的分片文件与恢复检查点一起被删，客户端后续 `PATCH/GET` 收到 404/资源隐藏，只能整段重传；与「清理失败保留检查点」的修复方向相反。
- 修复建议：只有 `errResourceHidden`（确定不存在）、`errResumeCorrupt`（确定损坏）、解析成功且确已过期/账户停用才删除；其他读取错误记录并跳过本轮，保留文件与检查点。
- 置信度：中高（静态确定；触发依赖数据库错误或关闭时序）。

### B-151（P3）`routeMethods` 每次调用重建 40+ 项映射并 `Split`，成为每请求的固定分配

- 位置：`http_methods.go:21-44`；调用点 `server.go:89-97`（尾斜杠归一）、`:338-344`（方法门禁）、`methodNotAllowed`（`http_methods.go:8-18`）。
- 证据：`exact := map[string]string{...}` 是函数内字面量，`strings.Split(allow, ", ")` 在门禁处还会再分配；一次普通 API 请求至少调用 2 次，错误方法请求 3 次。
- 影响：热路径的 map 构造与字符串切片分配增加 GC 压力；无正确性问题，属可观测的性能小事。
- 修复建议：把精确路由表与预拆分的方法集合提升为包级变量（或 `map[string][]string`），仅动态分支保留计算。
- 置信度：高（静态）。

### B-152（P3）容量页按账户 N+1 聚合位于 5 秒快照内，账户多时整页 500

- 位置：`storage.go:240-287`（`readQuery` 5 秒），`:275-285` 对每个账户调用 `accountStorageBreakdown`；出口 `storage_http.go:136-144` 统一 `500 STORAGE_READ_FAILED`。
- 证据：账户列表先查全部用户，再逐账户执行一次引用聚合；无分页、无超时降级。账户数 × 引用量增大时，超过 5 秒即整体失败，管理页无法查看任何容量数据。
- 影响：多用户实例的容量页/审计需求不可用，且错误无 `Retry-After`、无部分结果；与「容量页只读投影、快速返回」的声明不符。
- 修复建议：一条 `GROUP BY owner` 查询取全部分项（或缓存聚合）；快照超时时返回已取得的部分数据并标注不完整，而非整页 500。
- 置信度：中（规模依赖）。

### B-153（P3）删除被活动任务占用的预览返回 500，而非可重试的冲突语义

- 位置：`staging.go:678-680`（`errResumeBusy`）；出口 `server.go:1557-1564` 只把 `os.ErrNotExist` 映射 404，其余一律 500 `STAGE_DELETE_FAILED`。
- 证据：`DELETE /api/v2/uploads/stage/{id}` 在分片/完成处理持有该暂存路径时返回 `errResumeBusy`，HTTP 层无对应分支；客户端把 500 当服务端故障。
- 影响：并发下的正常竞争被表示为内部错误，自动化与前端无法据此退避重试；错误码契约缺失。
- 修复建议：`errResumeBusy` 映射 409（或 423）并给出稳定错误码/`Retry-After`，同步 HTTP 矩阵测试。
- 置信度：高（静态）。

### B-154（P3）账户临时资源丢弃在删文件前写入审计，「已丢弃」与实际可能不一致

- 位置：`account_temporary_cleanup.go:95-99`（事务内 `auditMutation("account.temporary_discard")`）与 `:103-116`（提交后删文件并 `errors.Join`）。
- 证据：审计行在 SQL 提交时即生效；随后逐文件 `root.Remove` 失败会让 `discardAccountTemporary` 返回错误，`PurgeUser` 因此中止（账户未删），但审计已记录「已丢弃预览」。
- 影响：失败时审计与磁盘状态不一致；孤儿文件依赖 `.staging` 生成名扫描稍后回收（`staging.go:755-767`），管理员从审计看不出「记录已删、文件待清理」，排查成本增加。
- 修复建议：文件删除失败时追加一条补偿性审计/状态（如 `account.temporary_discard_incomplete`），或在错误信息中区分「记录已丢弃、文件清理待重试」；保持先提交后删文件的顺序不变。
- 置信度：高（静态）。
