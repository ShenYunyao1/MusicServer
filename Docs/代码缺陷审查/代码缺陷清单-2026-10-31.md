## 一、P1 / P2 条目

### B-01（P1）封面资产不占配额、无回收、无磁盘预留检查，任意登录账户可无限膨胀 SQLite 直至数据盘耗尽

- **位置**：`server/internal/music/cover_store.go:105-117,195-200`；`server/internal/music/server.go:812-818,134-143`；`server/internal/music/storage.go:165-211`；`server/internal/music/sqlite.go:46`
- **证据**：
  ```go
  // cover_store.go:195-200 —— 只有插入，全仓库无删除 cover_assets 的 SQL
  func saveCover(tx *sql.Tx, data []byte, mime string) error {
      if len(data) == 0 || mime == "" { return nil }
      _, err := tx.Exec("INSERT OR IGNORE INTO cover_assets VALUES(?,?,?)", hashBytes(data), mime, data)
      return err
  }
  ```
  ```go
  // server.go:812-818 —— 创建歌单（multipart 封面）只要求账户会话
  case http.MethodPost:
      if !a.requireAccount(response, request) { return }
      if strings.HasPrefix(request.Header.Get("Content-Type"), "multipart/form-data") {
          a.playlistEditor(response, request, "")
  ```
  `savePlaylistEditor` 只校验封面是 ≤8 MiB、≤1024×1024 的方形 PNG/JPEG，然后直接 `saveCover`，不调用 `checkSpace`/`checkAccountQuota`；账户配额仅统计 `tracks` 对应音频文件的实际大小（`storage.go:165-194`）。
- **触发**：任意已登录成员（不要求邮箱验证或上传资格）循环执行 `POST /api/v2/playlists`（multipart，`cover` 使用每次不同的 1024×1024 PNG），或对同一歌单反复 `PUT /api/v2/playlists/{id}/editor` 更换不同封面。每次都插入一条新的 `cover_assets`（3–8 MiB BLOB），旧资产永不删除；歌单数量与封面总字节均无上限。
- **影响**：数据库（含备份复制）无界增长，可填满数据盘，导致全站写入、审计、备份失败。该路径绕过账户配额与容量统计，也绕过了 `checkSpace` 的数据盘预留检查；“删除封面/删除歌单”只清 `CoverID`，资产不释放。
- **修复建议**：为封面/附件建立账户级配额或全站上限；对 `cover_assets` 做引用计数或定期 GC；写库前检查数据盘余量；限制歌单创建和封面编辑频率。
- **置信度/验证**：高（代码路径与缺失的清理/配额逻辑均已在源码确认）；未做实际压测。

### B-02（P2）登录限流在反向代理部署下退化为全站共享 30 次/分钟桶，可被任意人锁死所有登录

- **位置**：`server/internal/music/auth_http.go:150-154`；`server/internal/music/accounts.go:216-243`；`server/internal/music/client_address.go:12-30`；`server/deploy/nginx.conf.example:36`
- **证据**：
  ```go
  // auth_http.go:150-154 —— 直接使用 RemoteAddr，未用 requestClientIP
  ip, _, err := net.SplitHostPort(request.RemoteAddr)
  if err != nil { ip = request.RemoteAddr }
  user, session, token, err := a.store.Login(body.Username, body.Password, ip)
  ```
  ```go
  // accounts.go:226 —— IP 桶上限 30 次/分钟
  {"user/" + hashSecret(username), 5}, {"ip/" + hashSecret(ip), 30},
  ```
  对照：注册和邮箱验证码发送使用 `a.requestClientIP(r)`（`registration_http.go:54`、`email_http.go:69`），该 helper 专为“反代回环 + 单值 X-Forwarded-For”设计；官方 Nginx 模板设置 `proxy_set_header X-Forwarded-For $remote_addr`。
- **触发**：按官方模板部署（Nginx → `127.0.0.1:8080`）后，所有请求的 `RemoteAddr` 都是 `127.0.0.1`。任意未登录者连续发送 30 次错误登录，即可在 1 分钟窗口内让所有用户在登录时收到 `429 LOGIN_LIMITED`；持续发送可持续拒绝登录。
- **影响**：公网部署下登录 IP 限流失效（退化成一个共享桶），既无法按来源限流，又形成可被外部触发的全站登录 DoS。README 已说明“代理后的登录 IP 限流以代理连接地址计”，但未说明会退化为共享桶及可被用于锁死登录；同时与注册/邮件接口的实现不一致。
- **修复建议**：登录复用 `requestClientIP`；或在反代部署下改为按账号 + 代理提供的可信来源 IP 分桶；对超限只限制该来源而不是全站。
- **置信度/验证**：高（代码事实）；未在真实反代环境复现。

- **位置**：`server/cmd/musicserver/admin.go:43-66`；`server/cmd/musicserver/runtime.go:10-13`；`server/cmd/musicserver/main.go:39-45`；`server/internal/music/store.go:94-97`；`server/internal/music/upload_resume.go:233-241,835-857`
- **证据**：

  ```go

  `NewStore` 总会执行 `InitializeResumableUploads`（`store.go:94-97`），后者对未过期的 `state=uploading` 任务调用 `recoverResume`，并把 `errResumeCorrupt` 持久化为 `task.State="corrupt"`（`upload_resume.go:844-849`）。

- **修复建议**：为 `admin` 子命令增加 `-media-root`（与服务端同义），或在 `NewStore` 初始化前从数据库设置读取已持久化的媒体根并校验；无法匹配时不要写 `corrupt`，应保留原状态并提示管理员传入正确路径。
- **置信度/验证**：高（代码路径确定）；未实际执行 CLI 复现。

  `ResetMemberPassword` 只有 `requireAdminActor`（校验操作者仍是启用管理员），不校验其会话是否已被撤销；`main.go:159` 的 `http.Server` 只设置 `ReadHeaderTimeout`，没有 `ReadTimeout`。
- **触发**：管理员会话（Cookie+CSRF）被窃取后，攻击者发起 `PUT /api/v2/admin/settings`（或重置成员密码、资源接管、存储策略）并故意只发送一半 body 后挂起；真实管理员在别处登出/撤销会话/改密；攻击者补发剩余 body。入口 `requireAdmin` 已在挂起前通过，后续 store 方法不再复核会话。
- **影响**：会话撤销无法立即阻断已鉴权的慢请求；可完成设置修改，或重置任意成员密码拿到一次性临时密码（接管成员账号）。更新与备份链仍有签名/角色边界，不是 RCE，但属于失败关闭（fail-closed）缺口，且项目在部分接口已实现事务内复核，属实现不一致。
- **修复建议**：对所有管理员写操作在事务内统一调用 `validateAccountMutationSession`（或等价会话/`auth_version` 复核）；为服务器设置 `ReadTimeout`/限制请求体读取时长。
- **置信度/验证**：中高（代码缺失确定；利用需已持有管理员会话，属于撤销后的窗口）。

## 四、已排除的误报方向（本次审计的阴性结论）

- **认证/授权绕过**：Cookie 与 API Key 不混用、失败不回退；Key 的 role 恒为 `player`，非 GET/HEAD 被 `playerEndpoint` 限制；`/admin/*` 均要求 `requireAdmin`（多数还有 `requireAdminActor`）；首次改密白名单仅 4 条，Key 认证拒绝强制改密账户；未发现越权读写他人歌单/暂存/Key。
- **CSRF / Origin**：会话写请求必须同源 Origin/Referer + 常量时间 CSRF 比较；`SameSite=Strict`；登录/注册/初始化各自校验 Origin。
- **路径穿越**：媒体读取使用 `os.OpenRoot` + 相对路径；暂存/恢复/备份路径均有 `IsLocal`/白名单；未发现 `..`/符号链接逃逸。
- **XSS**：内嵌网页对服务端可控字段使用 `textContent`/`txt()` 转义，未发现未转义的 `innerHTML` 注入点。
- **邀请/订阅状态机**：pending/accepted/declined/revoked、撤回/再次邀请、接管后强制私有、取消订阅清 Key 授权等路径核对通过。
- **签名更新链**：清单 Ed25519 验签、包大小/SHA-256 双重校验、tar 白名单、queue 路径 `os.OpenRoot`、回滚时程序/数据库版本配对均自洽；未发现可远程绕过点。
- **迁移/恢复**：schema 7→8 快照、完整性/外键检查、空目录恢复、路径白名单、会话/暂存清理核对通过。
- **写事务**：业务写路径统一走 `s.transaction`（writeMu + defer Rollback），未发现未回滚的部分提交；标签写使用独立 `tagTransaction`。

  const metadata=/^\[(?:ar|ti|al|by|re|ve|length|id):[^\]]*\]\s*$/i;
  // :32 —— 无时间戳的行进入 notes
  else{plain.push({time:null,text});if(text)notes.push({time:null,text})}
  // :34 —— 有时轴歌词把 notes 追加到末尾
  if(timed.length){timed.sort(...);return {timed:true,lines:timed.concat(notes)}}
  ```
  `[kuwo:033]`、`[ver:v1.0]`、`[awlrc:lrc:<base64>]`、`[tlrc:...]`、`[rlrc:...]` 都不匹配该白名单；当行没有前导 `[mm:ss]` 时间戳时，被当作“无时间歌词”。
- **复现**：用 Node `vm` 直接加载 `lyrics-parser.js` 解析仓库内样本：
  - `可愛くてごめん...lrc` 的尾部结果为 `{time:null, len:19999, head:"[awlrc:lrc:W29mZnNldDowXQpbMDA6MDAuOTE2X..."}`；
  - `秋风词 - 司南.lrc` 尾部追加 `[kuwo:033]`、`[ver:v1.0]`。
  `online-player.js:77` 把 `time===null` 的行渲染成 `<p>`，原始标签/Base64 直接显示在歌词组件底部。
- **影响**：含扩展标签的 LRC 会在歌词面板尾部显示大量原始数据（样本近 2 万字符），遮挡正常歌词并增加滚动/布局负担；内容通过 `textContent` 渲染，不构成 XSS。所有来源含 `awlrc/tlrc/rlrc/kuwo/ver` 等标签的曲目都会受影响。
- **修复建议**：无时间戳分支过滤通用元数据前缀（如 `/^\[[A-Za-z][A-Za-z0-9_]*:/`），并对 `awlrc/tlrc/rlrc` 明确忽略；有时轴时不把元数据样式行追加到 `notes`；对超长行设置上限；在 `server/tests/lyrics-parser-test.cjs` 增加真实标签用例。
- **置信度/验证**：高；已运行时复现解析结果，发布版页面渲染路径与源码一致。

### B-35（P2）扩大勾选热区后，按下在热区、抬起跨过封面左缘会取消勾选失败并打开曲目详情

- **位置**：`server/internal/music/track-interaction.js:5-9,13-23`；`server/internal/music/selection-ui.js:82,89-92`；行/复选框结构 `server/internal/music/library.js:33-35`；热区样式 `server/internal/music/selection-ui.css` 中 `.track-selection-cell` 的 44px 规则
- **证据**：
  ```js
  // track-interaction.js:5-9 —— 只按坐标判定热区
  return input&&...&&x>=rect.left&&x<cover.getBoundingClientRect().left&&y>=rect.top&&y<=rect.bottom?input:null;
  // :13 pointerdown 命中后取消待定单击
  // :15 click 再次用“抬起点”坐标判定；失败则 return
  // :16-23 行单击处理器：空白/标题区域 400ms 后 detail()
  ```
  `selection-ui.js:82` 约 6px 才进入拖选；`:89-92` 只有真正拖动才抑制后续 click。因此按下在热区内、抬起点跨过 `cover.left` 但位移小于 6px 时，拖选不抑制 click，行单击处理器接管并打开详情。
- **复现**（v0.21.9 发布程序，Chromium 1208，临时隔离库，第一条曲目）：
  | 操作 | 结果 |
  | --- | --- |
  | 热区内按下并原地抬起 | `checked=true, detailsOpen=false`（正常勾选） |
  | `coverLeft-2` 按下，向右移 4px 到 `coverLeft+2` 抬起 | `checked=false, detailsOpen=true`（未切换勾选，打开详情） |
  | 热区中部按下拖到 `coverLeft+2`（>6px） | `detailsOpen=false`（拖选抑制 click） |
- **影响**：热区右缘靠近封面的十余像素区域内，点击/取消勾选会因轻微位移变成“打开本项详情”；违反“扩大热区不打开详情”的既定要求，用户会感到取消勾选无效并弹出遮挡弹窗。
- **修复建议**：`pointerdown` 记录本次是否命中热区及对应 input；`click` 时若按下命中且位移在阈值内，直接执行 `toggle()` 并阻断行单击/封面播放，不再用抬起坐标重算；把 `.track-selection-cell` 及热区命中路径从 `isBlank()` 的空白单击/双击详情判断中排除；在 `pointerup/pointercancel/scroll/blur/hashchange` 清理按下状态；在 `server/tests/track-interaction-ui.cjs` 增加“按下在热区、抬起跨封面边界”的回归用例。
- **置信度/验证**：高；已在真实 0.21.9 UI 用可信鼠标事件复现。
