# 未来功能规划

日期：2026-10-27。承接 [曲目标签与组合筛选开发计划](曲目标签与组合筛选开发计划.md)。用户同意将后续能力单独记录，并提出未来加入 AI 调用筛选；本文件为方向与边界记录，不代表已授权实现、开通服务、发送外部数据、付费、推送或发行。

当前服务器基线为 0.20.2、播放器 0.4.0。标签、组合筛选和保存条件的一期交付不依赖本文件任何功能完成。下面均未实施，优先级和最终规格在对应阶段开始前确认，不承诺日期。

## 一、外部资料辅助补全

- [ ] F01：接入可配置的 MusicBrainz／AcoustID 元数据候选流程。

利用现有元数据、外部录音标识或音频指纹匹配资料，展示候选录音、来源及待修改字段，由用户确认后应用。优先补缺失信息；已手工确认、明确忽略的值和个人标签保留。匹配分数用于排序，不等同于准确率；不同发行、现场、翻唱和重混需明确区分。

外部录音标识是辅助关联，不替换服务器曲目 UUID，不按匹配结果自动合并或删除不同音频。匹配录音与判断情绪是不同能力，不用曲名／歌手推断真实听感。

后台任务应支持进度、取消、缓存、失败重试和服务限流，不能阻塞上传校验；明确所需 API 凭据及外部发送的数据。MusicBrainz 当前公开接口通常按来源 IP 平均每秒一次限制，并要求有意义的 User-Agent，应在实施时重新核对。

参考：[Picard 音频指纹](https://picard-docs.musicbrainz.org/en/latest/config/options_fingerprinting.html)、[Picard 风格来源](https://picard-docs.musicbrainz.org/en/v3.0/config/options_genres.html)、[MusicBrainz 限流规则](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)。

## 二、智能歌单及播放器使用

- [ ] F02：把已保存筛选条件升级为按规则维护成员的智能歌单。

复用一期结构化条件，例如“日语＋电子＋我的通勤标签＋排除现场”。曲库或标签变化后更新成员及版本，通过现有歌单／增量接口供播放器使用，不要求播放器自行实现完整筛选引擎。

需要明确刷新触发、结果上限、稳定排序和成员变化语义；保留既有只读／订阅规则，API Key 仍由用户显式授权。创建规则不自动赋予 Key 访问权。包含个人标签的规则默认仅本人可用；公开／分享前必须另行定义权限和隐私处理，不能通过公开结果泄露私人整理。

参考：[beets 智能歌单](https://docs.beets.io/en/stable/plugins/smartplaylist.html)、[Navidrome 规则歌单](https://www.navidrome.org/docs/usage/smartplaylists/)。

## 三、音频模型辅助打标

- [ ] F03：评估风格、情绪、乐器、人声等音频分析模型。

可参考 Essentia 等音乐分析工具生成带模型评分的标签建议；自动推断与人工确认分别保存，默认进入待确认区，允许拒绝且不被下一次分析反复覆盖。

评估服务器 CPU／内存、并发、模型大小、音频时长、语言覆盖、推理耗时和标签准确性后，决定本地计算或可选外部服务。记录模型与词表版本，缓存有效分析结果；不在用户上传的同步校验阶段执行昂贵推理，不因重新分析重复传输整首音频。

工具与模型许可分别核对，不能把软件开源理解为所有模型均可任意使用。Essentia 官方说明其 MTG 模型含 CC BY-NC-SA 4.0 条件；实际选型时重新确认具体权重许可。本阶段不预选付费服务或更换云服务器规格。

参考：[Essentia 官方模型目录](https://essentia.upf.edu/models.html)。

## 四、AI 调用筛选

- [ ] F04：自然语言生成可编辑的筛选条件。
- [ ] F05：在已授权候选曲目范围内进行可解释的辅助选择／排序。

用户新增方向示例：

```text
找一些适合夜间驾驶的日语电子音乐，排除现场版。
从我的收藏中挑出带人声、时长五分钟以内的舒缓音乐。
```

推荐先实现“自然语言 → 已知字段和标签 ID 的结构化筛选条件 → 服务端验证 → 展示条件并应用”。复用一期确定性查询，不把整套检索逻辑交给模型。模型只能选择实际存在的字段、运算符、标签和有权读取的资源，不能生成任意 SQL 或绕过权限。

模型生成的条件在页面可见、可修改，保留模型解释及无法满足的条件。缺少情绪、场景或人声信息时明确说明，不把标题推断当作已分析的音频事实。没有匹配结果时不能静默放宽排除条件或扩大访问范围。

后续可对确定性筛选得到的有限候选集提供辅助排序或挑选，输出必须引用真实曲目 UUID，并由服务器再次校验访问权限。普通文本模型的筛选／排序与 F03 的音频模型打标是两个独立模块；自然语言入口不表示系统已经听过并理解所有音乐。

外部模型接入前需要确定：管理员可控的启用开关、服务商及模型配置、凭据受限保存、每账户调用额度、费用／超时上限、可发送字段、数据保留设置和失败回退。优先仅发送必要的条件词典和少量授权摘要，个人标签、资料和原音频不默认整库外发；相关发送方式在该阶段明确确认。

权限过滤始终由服务器完成，不依赖模型自觉遵守。模型返回内容和曲目文本均按不可信输入处理；默认只有只读查询能力，不授予修改标签、歌单、账户或 Key 的权限。AI 故障不影响普通搜索和已有筛选。

## 五、可选的播放器整理体验

- [ ] F06：播放器展示公共分类、本人标签或保存筛选入口。

先保证旧播放器继续通过既有歌单播放；再按需求决定是否提供受账户／Key 授权约束的标签协议及客户端界面。个人标签不可进入跨账户共享缓存，授权撤销和切换账户时同步清理可见状态。若需要播放器直接调用 AI，还须单独设计权限、限额和服务凭据边界，不让播放器持有服务器的模型服务密钥。

## 六、后续推进规则

建议顺序为：完成标签一期 → 外部资料补全及智能歌单 → 评估 AI 自然语言筛选 → 视效果与资源决定音频模型和播放器扩展。AI 筛选的实施顺序可独立于音频模型调整。

每项开始前确认实际需求、外部依赖和验收标准，并拆为独立开发计划。完成验证后才勾选并本地提交；推送、正式发行及云端维护均遵循当次明确授权。本文件当前所有功能项保持未完成状态。
