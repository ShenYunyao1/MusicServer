# 音乐服务器与多端播放器方案调研

更新时间：2026-10-07

## 结论

方案可行，而且适合分阶段实现。推荐把系统拆成三个相对独立的部分：

1. **音乐服务器**：负责文件存储、媒体库扫描、元数据/歌词、歌单、分类、注释、用户和增量同步。
2. **桌面客户端**：在现有 `MusicPlayer2` 的播放内核和 UI 基础上增加远程媒体库、缓存和同步适配层。
3. **ESP32-S3 客户端**：只实现轻量的设备 API、下载缓存和 I2S 播放，不承担完整媒体库管理。

服务器不应被设计成“把桌面播放器的本地文件路径暴露到网络上”。服务器保存稳定的曲目 ID、内容哈希和版本号，客户端通过 ID 获取元数据、歌词和音频；这样本地部署、云部署、断网缓存和 ESP32 都能使用同一套数据模型。

## 对现有 MusicPlayer2 的判断

GitHub 项目：<https://github.com/zhongyang219/MusicPlayer2>

- 项目是 **C++/MFC、仅面向 Windows** 的本地播放器，构建说明要求 Visual Studio 2022 和 MFC。
- 已有可复用能力：`Player` 播放队列和播放状态、`IPlayerCore` 播放内核抽象、`AudioTag`/TagLib 标签读写、`CLyrics` 歌词解析、媒体库、`CInternetCommon` HTTP 请求工具。
- 播放列表和媒体库当前主要以本地文件路径为中心；远程曲目需要引入虚拟文件/缓存路径或新的媒体源抽象。
- 因此最稳妥的改法是增加 `RemoteTrackSource`、`RemoteLibraryClient`、`CacheManager` 三层，让 `Player` 最终仍然播放一个本地缓存文件。不要在 UI 代码中直接拼接服务器 URL。
- 仓库许可证为 GPL-3.0。若直接修改并分发该客户端，需要遵守 GPL-3.0；新服务器可以单独选择许可证，但复用客户端代码时应保留许可证和版权要求。

## 开源实现带来的设计结论

### Navidrome

Navidrome 是低资源、自托管、跨平台的音乐服务器，支持 Docker、自动监视媒体库变化、元数据和多种歌词文件、转码，并兼容 Subsonic/Madsonic/Airsonic 客户端。

参考：<https://github.com/navidrome/navidrome>、<https://www.navidrome.org/docs/developers/subsonic-api/>

它适合作为“先验证远程播放和部署”的现成服务器，但它的管理模型和扩展点未必覆盖曲目/歌单注释、设备同步策略等定制需求。因此建议把 Navidrome 作为兼容性参考或临时验证工具，不把自定义功能强行做成 Navidrome 插件。

### LMS

LMS 是 C++ 实现的轻量音乐服务器，支持 OpenSubsonic、播放列表、歌词、多用户、转码、MusicBrainz ID 和多值标签。

参考：<https://github.com/epoupon/lms>

它说明“以 MusicBrainz ID 处理重复艺术家/发行版本”和“以标签而不是路径组织媒体库”是值得采用的建模方式。

### OpenSubsonic

OpenSubsonic 提供事实上的客户端互操作基础：

- `stream`：按曲目 ID 流式播放，可协商格式/码率。
- `getPlaylists`、`getPlaylist`：读取歌单及曲目。
- `getLyricsBySongId`：读取同步歌词、翻译和多语言歌词。
- `getScanStatus`：查询媒体库扫描状态。
- `apiKey` 扩展：适合 ESP32 这类不方便处理复杂登录流程的设备。

参考：<https://opensubsonic.netlify.app/docs/endpoints/stream/>、<https://opensubsonic.netlify.app/docs/endpoints/getlyricsbysongid/>、<https://opensubsonic.netlify.app/docs/endpoints/getplaylists/>、<https://opensubsonic.netlify.app/docs/extensions/apikeyauth/>

建议：服务器实现 OpenSubsonic 的读取/播放兼容层，同时增加自己的 `/api/v1` 管理和增量同步 API。这样可以复用已有客户端生态，又不会把自定义需求限制在旧协议里。

### ESP32 音频栈

可选实现包括：

- Espressif ESP-ADF/ESP-GMF：官方音频应用框架，适合需要完整音频管线、服务和产品化管理的实现。ADF 3.0 与 ADF 2.x 不兼容，应固定版本，不要混用示例。
- `ESP32-audioI2S`：已验证在多核 ESP32-S3 上工作，支持 MP3、AAC、FLAC、Opus、Vorbis，支持 HTTP 播放和 I2S 输出，适合先做原型。

参考：<https://github.com/espressif/esp-adf>、<https://github.com/schreibfaul1/ESP32-audioI2S>

ESP32-S3-N16R8 的重点约束是 RAM、Flash、网络抖动和外部音频硬件，而不是服务器协议本身。建议使用 HTTPS 下载、分块写入 Flash/SD、预留播放缓冲，优先支持 MP3/AAC/Opus；FLAC 可作为高质量模式，需实测解码和功耗。

## 推荐总体架构

```text
                 ┌──────────────────────────┐
                 │  Web 管理界面 / REST API │
                 └────────────┬─────────────┘
                              │
┌───────────────┐    ┌────────▼─────────┐    ┌────────────────┐
│ MusicPlayer2  │◄──►│ 音乐服务器核心   │◄──►│ 文件/对象存储  │
│ Windows 客户端│    │ Go + SQLite/PG   │    │ 本地盘或 S3    │
└──────┬────────┘    └──────┬─────────┘    └────────────────┘
       │                    │
       │ 本地缓存播放       │ 扫描、标签、歌词、版本
       │                    │
┌──────▼────────┐    ┌──────▼─────────┐
│ ESP32-S3 播放器│    │ FFmpeg/扫描任务 │
│ Wi-Fi + Cache  │    │ MusicBrainz 等  │
└───────────────┘    └────────────────┘
```

推荐服务器技术栈：Go、SQLite（单机默认）/ PostgreSQL（多人或云部署）、本地文件系统（默认）/ S3 兼容对象存储、FFmpeg（可选转码）、Docker Compose。Go 单二进制便于 NAS、Windows、Linux、云主机部署；SQLite 足以支撑个人库，部署到云端后再切换 PostgreSQL。

## 核心数据模型

服务器数据库至少包含：

- `tracks`：稳定 `id`、内容哈希、相对存储键、标题、艺术家、专辑、专辑艺术家、碟号/曲号、年份、流派、时长、编码格式、采样率、文件大小、更新时间。
- `track_external_ids`：MusicBrainz recording/release/artist ID、ISRC 等外部 ID。
- `lyrics`：曲目 ID、语言、纯文本/同步行、来源、版本、更新时间。
- `artworks`：封面哈希、尺寸、媒体类型、对象存储键。
- `playlists` 与 `playlist_items`：歌单、排序、曲目 ID、歌单注释、曲目在歌单中的注释。
- `tags` 与 `track_tags`：用户自定义分类，避免把所有分类硬编码为有限枚举。
- `library_revisions`：全局修订号或变更日志，用于增量同步。
- `users`、`devices`、`device_tokens`：用户权限、设备 API Key、撤销时间和最后同步位置。

文件更新不能只依赖路径或修改时间。推荐用 `sha256`（大库可先用文件大小+mtime，再后台补算哈希）作为内容版本；元数据/歌词/歌单更新分别产生版本号。

## API 分层

### OpenSubsonic 兼容层

第一阶段实现读取和播放相关接口：`ping`、`getArtists`、`getAlbumList2`、`getAlbum`、`getSong`/`getMusicDirectory`、`getPlaylists`、`getPlaylist`、`stream`、`getCoverArt`、`getLyricsBySongId`、`scrobble`。它满足桌面客户端和第三方客户端的基本连接能力。

### 自定义管理/同步 API

建议版本化为 `/api/v1`：

```text
POST   /api/v1/auth/login
GET    /api/v1/sync?since=<revision>&device_id=<id>
GET    /api/v1/tracks/{id}
PATCH  /api/v1/tracks/{id}
GET    /api/v1/tracks/{id}/lyrics
PUT    /api/v1/tracks/{id}/lyrics
GET    /api/v1/playlists
POST   /api/v1/playlists
PATCH  /api/v1/playlists/{id}
POST   /api/v1/playlists/{id}/items
DELETE /api/v1/playlists/{id}/items/{item_id}
POST   /api/v1/uploads/init
PUT    /api/v1/uploads/{upload_id}/parts/{part}
POST   /api/v1/uploads/{upload_id}/complete
GET    /api/v1/media/{track_id}/download
POST   /api/v1/admin/scan
GET    /api/v1/admin/scan/status
```

`sync` 返回新增/更新/删除的曲目、歌词、歌单及修订号；音频不放进同步响应，只返回大小、哈希和下载 URL。下载接口支持 HTTP Range、ETag、断点续传和可选转码。

## 歌词和元数据自动关联

推荐优先级：

1. 音频内嵌歌词/封面。
2. 同目录同基名的 `.lrc`、`.elrc`、`.ttml`、`.srt`、`.txt`。
3. 依据 MusicBrainz ID、标题、艺术家、专辑和时长向外部服务查询。
4. 人工确认候选结果，并记录来源、匹配分数和人工锁定状态。

自动关联必须可撤销，不能在每次扫描时无条件覆盖人工编辑。服务器保存规范化歌词，原始文件和外部来源信息可作为审计字段；客户端只读取服务器确认后的版本。

## 客户端缓存和同步策略

桌面客户端与 ESP32 都采用同一个基本流程：

1. 保存服务器地址、设备 ID 和 API Key。
2. 定期调用 `sync(since=last_revision)`，先更新本地曲目/歌单索引。
3. 用户播放时检查缓存中的内容哈希；命中则立即播放，未命中则下载到临时文件。
4. 下载完成后校验大小和 SHA-256，再原子重命名为缓存文件。
5. 缓存按 LRU、最大空间和“固定收藏”策略清理。
6. 网络失败时继续播放已缓存曲目；待网络恢复后重试同步和下载。

桌面端可以缓存较大的无损文件；ESP32 建议默认缓存当前曲目和接下来 1 首，歌单下载作为显式操作。不要让 ESP32 直接处理完整 JSON 歌词/媒体库；同步响应应支持分页、字段裁剪和压缩。

## MusicPlayer2 改造边界

建议按以下顺序改造，不先重写现有 UI：

1. 抽象 `IMediaSource`：本地文件和远程曲目都返回统一的 `SongInfo`。
2. 新增 `RemoteLibraryClient`：认证、分页查询、同步、歌单读写、歌词读取。
3. 新增 `CacheManager`：哈希命名、临时文件、Range 下载、校验、LRU 清理。
4. 在 `CPlayer::PlayTrack` 前调用“确保本地缓存”，成功后把缓存路径交给现有播放内核。
5. 在媒体库/歌单 UI 增加服务器来源标记和同步状态；保留现有本地文件模式。
6. 将现有 `CLyrics` 解析器用于服务器返回的 LRC/结构化歌词，避免重复实现歌词时间轴。

现有 `CInternetCommon` 可以作为第一版 HTTP 封装，但长期建议换成支持 TLS、超时、取消、Range、响应流式写入的独立客户端库（例如 libcurl 或 WinHTTP 封装）。

## MusicPlayer2 服务器选项卡交互方案

用户提出的入口设计：在设置中配置服务器，在媒体库新增“服务器”选项卡，选项卡中展示服务器歌单。推荐采用此布局。

### 与现有界面的对应关系

2026-10-07 阅读上游公开源码确认：

- `CMediaLibDlg::OnInitDialog` 使用 `CTabCtrlEx::AddWindow` 注册文件夹、播放列表、艺术家等子对话框，可沿用此模式注册新的服务器页。
- `COptionsDlg::OnInitDialog` 以同样方式注册设置页，可新增“服务器”设置页；建议追加到现有页之后，减少对已有设置页索引的影响。

- 新页还需要纳入窗口销毁、布局调整、本地化、状态保存和设置应用流程，并不只是增加一个标签标题。

### 设置 → 服务器

第一版配置一台服务器，保存显示名称、地址、账户或令牌、自动检查更新开关，以及缓存目录和容量上限。提供“测试连接”，明确区分地址不可达、认证失败和协议不兼容。

凭据使用 Windows 凭据管理器或 DPAPI 保护；普通配置文件只保存非敏感配置。修改地址或账户后使用独立的本地索引与缓存命名空间，避免不同服务器的相同曲目 ID 混淆。可预留多服务器结构，第一版无需增加切换界面。

### 媒体库 → 服务器

```text
媒体库：[文件夹] [播放列表] [艺术家] … [服务器]

服务器：我的音乐库        在线 · 上次同步时间    [刷新] [设置]
┌────────────────┬─────────────────────────────────────┐
│ 歌单           │ 歌单名称与注释                       │
│ 我的收藏       │ 标题 / 艺术家 / 时长 / 缓存状态       │
│ 通勤           │ 曲目 A … 已缓存                      │
│ 学习           │ 曲目 B … 未缓存                      │
│                │ 曲目 C … 下载中                      │
└────────────────┴─────────────────────────────────────┘
                  [播放] [加入播放队列] [离线保存歌单]
```

左侧歌单、右侧曲目和歌单注释。双击曲目播放，右键支持加入队列、缓存所选曲目、查看曲目注释；歌单级操作提供播放整个歌单和离线保存。后续再增加服务器端歌单编辑、分类与上传入口。

“播放缓存”允许容量不足时自动清理；“离线保存”固定保留，直到用户解除保存。清理缓存不等于删除服务器曲目，歌单移除条目也不等于删除服务器音频。

### 同步与播放行为

- 未配置：显示“尚未配置服务器”和进入设置的按钮。
- 已配置：先展示本地保存的歌单快照，再后台检查更新；支持手动刷新和可配置的低频检查。
- 断网：展示最近一次歌单快照及离线状态；已缓存曲目可播放，未缓存曲目提示需要联网。
- 歌单更新：更新浏览页，保留当前正在播放的曲目；当前队列默认保留用户开始播放时的快照，用户重新播放歌单时采用最新版本。
- 下载失败：显示可重试的错误，保留临时文件供断点续传；取消下载不会把临时文件标记为完整缓存。

第一版可先实现整首下载后播放，以验证缓存和现有内核集成。若要求点击即播并同时缓存，则需单独实现渐进下载与播放：协调缓冲、未下载区间的跳转、断网重试和播放内核读文件行为；不能假定已有内核能安全读取仍在写入的文件。

### 第一版验收

设置并测试连接成功 → 打开服务器选项卡看到歌单 → 选择歌单看到曲目与注释 → 播放并生成缓存 → 服务器修改歌单后刷新可见 → 断网播放已缓存曲目。完整的上传与元数据编辑仍属于后续管理功能。

## ESP32-S3 实施建议

硬件层至少需要：Wi-Fi、外部 I2S DAC/功放（例如 MAX98357A 单声道或 PCM5102A/UDA1334A 立体声）、用于缓存的 SD 卡或足够大的外部 Flash、按键/旋钮和显示屏（按产品需求）。

软件层建议：ESP-IDF 固定版本，原型阶段可使用 `ESP32-audioI2S`，产品化再评估 ESP-ADF/ESP-GMF；网络任务、下载任务、解码/I2S 任务分离；所有下载使用 TLS、Range 和校验；API Key 可撤销、设备丢失后可禁用。

ESP32 第一版只实现：登录/设备注册、获取歌单、获取曲目摘要、下载 MP3/AAC、播放/暂停/切歌、基本歌词显示、缓存状态。不要第一版加入转码、完整标签编辑、上传和复杂推荐。

## 分阶段路线

### Phase 0：验证（1 周左右）

- 用 Navidrome 或 LMS 在本地 Docker 启动服务器。
- 从 MusicPlayer2 读取 OpenSubsonic 歌单和 `stream`，验证缓存后播放。
- 用 ESP32-S3 播放一个固定 HTTP/HTTPS 音频 URL，确认 I2S 硬件、缓冲和功耗。

### Phase 1：可用 MVP

- 自建服务器：扫描目录、标签、封面、LRC、歌单、用户登录、Docker 部署。
- 实现 `/api/v1/sync`、断点下载、哈希校验、服务器端歌单注释。
- MusicPlayer2 支持服务器歌单和本地缓存，保留本地库功能。

### Phase 2：管理和自动化

- Web 管理页：上传、编辑标签、编辑歌词、分类、批量操作、扫描任务状态。
- MusicBrainz/歌词服务候选匹配，人工确认和锁定。
- 多用户权限、设备管理、播放历史和收藏同步。

### Phase 3：ESP32 产品化

- 固化设备 API 和缓存协议，增加 OTA、断网策略、低功耗和错误恢复。
- 根据实测决定 MP3/AAC/Opus/FLAC 支持范围和是否需要服务器转码。
- 增加播放控制、歌词显示、歌单离线下载和设备端配置。

## 主要风险与应对

- **协议重复造轮子**：先兼容 OpenSubsonic，定制能力放在版本化自有 API。
- **外部歌词/元数据服务不稳定或有配额**：缓存结果、限速、记录来源，始终允许人工编辑。
- **云端暴露音频接口**：全程 HTTPS、短期下载 URL 或 API Key、按用户/设备授权、Range 限速和日志审计。
- **桌面播放器线程模型复杂**：网络下载不得阻塞 UI 或播放线程，先落临时文件再原子切换。
- **ESP32 内存与网络抖动**：限制响应字段、分页、流式下载、外部存储缓存，优先稳定支持少量编码格式。
- **本地与服务器同时编辑**：第一版采用“服务器为媒体库权威、本地播放器只读同步”；离线编辑放到后续，引入操作队列和冲突策略。

## 建议的第一个可验证目标

先完成一个竖切片：

> Docker 启动服务器 → 上传/扫描一首 MP3 和一个 LRC → 创建歌单 → MusicPlayer2 登录并同步歌单 → 首次下载到缓存并播放 → 断网后再次播放同一曲目。

这个目标能同时验证数据模型、认证、增量同步、缓存、歌词和播放内核集成，完成后再扩展批量管理和 ESP32 UI。
