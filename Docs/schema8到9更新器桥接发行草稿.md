# schema 8→9 更新器桥接发行草稿

2026-11-02。本文件记录后续正式发行的依赖和验收，不授权推送或发布，也不表示已经生成桥接包。当前本地工作树的数据库目标为schema 9，原schema 8账户、Key、曲目、歌单与标签通过备份和事务迁移保留。

## 为什么需要桥接

已发布的旧schema 8主程序与独立更新器只识别schema 7、8。只有新的主程序兼容策略、签名发行清单和独立更新器能力同时支持8→9，网页检查和安装才能安全进行。单独改清单、只替换worker、或直接执行schema 9包中的同schema维护命令都不能跳过这个要求。

## 正式发行前顺序

1. 准备单独的schema 8桥接提交和版本B：仍使用schema 8数据库，但包含本次已实现的schema 9清单解析、8→9兼容策略、worker能力校验及迁移／恢复验证。桥接阶段应隐藏听歌统计界面并拒绝统计接口，不能访问尚不存在的三张表。
2. 在干净提交上，以正常Actions门禁构建、签名并发布B；签名清单、两个包及程序VCS身份须一致。不得把修改版本常量的本地程序冒充正式桥接资产。
3. 现有schema 8安装先通过其现有更新能力安装B主程序，确认版本B／schema 8及原有数据。创建并保留完整备份。
4. 维护者使用经过固定可信公钥验签、大小与SHA-256核对的B Linux包，在root拥有且其他用户不可写的解包目录执行：

   ```sh
   sudo ./musicserver-updater -config /etc/musicserver/updater.json -refresh-worker B
   ```

   其中B须替换为真实正式桥接版本，不是字母占位符。维护前无活动安装、回退或维护标记；未知中断先诊断，不删除状态强行继续。维护命令要求当前主程序与维护程序同schema，禁止从schema 9解包程序直接维护仍在schema 8的安装。
5. 核验能力文件对应正式B版本／提交，包含schema 8、9以及明确的8→9迁移。旧能力或缺失能力应明确阻止安装，不能“尽力继续”。
6. 再准备更高版本V／schema 9的正式候选，清单仅声明`migrate_from: [8]`。通过8→9真实数据保留、systemd健康失败回退／中断恢复、网页及播放器门禁，再签名发布。桥接版网页方可检查并由用户确认安装V。

更新器停止服务、备份源schema 8数据库，切换主程序；新主程序启动前另存独立8格式快照，事务创建听歌统计表并记录唯一迁移。健康检查同时核对版本、提交和schema。失败恢复原程序及原schema 8快照，绝不让旧程序读取schema 9库，也不将回退解释为数据库降级迁移。

Windows手动替换程序时先停服及备份；新程序同样保留独立8格式快照并事务升级。首次安装直接创建schema 9新库，不产生旧库迁移备份。

## 本地验证与剩余边界

本地已覆盖明确8→9／拒绝无声明迁移和9→8、旧worker能力拒绝、8格式迁移备份、失败后DDL回滚与幂等、8备份恢复至9以及9备份保留统计与拒绝恢复至8。当前未进行外部发布或安装操作。

发布时必须确定真实B、V版本号并补充对应Release链接及验收结果。完整Linux race、真实systemd安装／回退、跨平台与两端联调依赖之后显式推送触发的Actions；Linux交叉编译不能代替实际systemd验收。
