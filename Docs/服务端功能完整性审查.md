# 服务端功能完整性审查

审查日期：2026-10-07。审查对象：**本轮升级前状态**，首次读取时服务端版本为 0.4.1。

本报告依据实际源代码与已有测试定义审查，不将设计文档、实施计划或依赖声明视为已经实现。工作区没有可供比较的不可变升级前快照，审查期间其他任务正在修改 SQLite、音频标签和管理页；因此本文记录首次读取时的状态，不代表本轮升级完成后的缺陷清单。下文行号为审查时定位，升级后请同时用函数名查找。新增修复的最终状态应另行记录，不能把本报告的升级前结论直接用于验收升级后版本。

## 0.5.0 修复状态

本轮已完成 SQLite 关系存储、音频标签和内嵌歌词读取、上传原子提交、零时间 Key 展示及网页认证测试修复。旧 JSON 兼容代码按新的产品决定移除：`.json` 数据路径会报错，SQLite 从空库初始化，旧媒体文件需要重新扫描。曲目列表现在展示真实标签中的专辑/风格，缺失标签显示为空，不再使用文件夹名。设备租约与并发限制、歌单排序持久化、设置页、封面/技术参数、上传暂存预览和调用统计仍未实现，以下 A1、A5、A6、A9 的相关结论仍然适用；A2、A3、A4、A10 中对应的已修部分应以 0.5.0 测试和 README 为准。

## 0.6.0 修复状态

2026-10-08 更新：7 项 scopes 已参与接口授权，请求并发上限已执行；歌单排序保存到 SQLite 并由列表与同步接口使用，普通歌单内容编辑保留服务器当前顺序。设置页、曲目封面/技术参数、上传暂存预览/确认/内容去重、外置资源关联及持久调用统计已实现。尾斜杠 Key 管理接口也检查 `keys:manage`；自动关联封面保留外置来源，避免覆盖内嵌或正确匹配的专辑封面。

本轮测试覆盖 schema v1 至 v2 关系数据升级、授权与并发生命周期、统计和设置持久化、排序后编辑及重启、真实本机歌词/标签/技术参数、图片校验、附件重扫与重启、失败恢复和暂存清理。实际浏览器验证上传预览不入库、确认、曲目封面、去重、歌单拖拽与右键子菜单、设置关闭保存、7 项 scope 复选框和默认并发 1 的持久管理员。MusicPlayer2 新增受认证的同名封面缓存，WinHTTP 黑盒回归和 Debug x64 构建通过。

仍未实现的能力：设备身份和心跳租约、独占客户端、歌单并发编辑冲突检测、网页成员排序/成员注释完整编辑、恢复移除记录的入口、后台扫描任务/目录监听、操作审计、转码和外部歌词平台。SQLite 当前仍保留全量内存快照及全量事务写入，扫描/上传占用媒体库锁，适用于个人单进程服务；接口请求并发限制不能据此解释为单设备授权。旧报告下文属于升级前记录，当前能力以本段、README 和 0.6.0 实施计划为准。

## 结论与范围

服务端已经形成可用的初版链路：目录扫描、同名歌词、人工元数据覆盖、歌单管理、歌单授权过滤、媒体下载和 MusicPlayer2 完整下载后播放/离线缓存。第二阶段的多 Key、管理员写入边界和歌单权限检查有实际实现；第三阶段的右键菜单、多选加入歌单和上传队列也有代码实现。

距离设计中的正式管理服务器仍有明显差距：设备与并发限制没有执行，scopes 没有参与授权；歌单排序没有持久模型，编辑没有冲突保护；上传没有暂存确认与重复识别；音频标签、封面、技术参数、任务设置与调用统计在升级前尚未齐备。另有 Key 状态误判、Web 调用测试误报成功和上传分两次提交的问题，需要优先处理。

## 优先问题与证据

### A1 · P1：配置中的 scopes、设备与并发限制没有实际效力

定位：`server/internal/music/types.go:43`（`APIKey`），`server/internal/music/server.go:25`（`authContext`）、`:118`（`authenticate`）、`:140`（`requireAdmin`）、`:148`（读取授权）。设备/并发字段仅见于数据结构与创建/更新，未进入认证上下文和请求控制；客户端 `RemoteLibraryClient.cpp:420` 只发送 Key，没有设备标识。

触发：管理员设置仅 `read_media` 的 scopes、指定设备或 `max_devices=1`/`max_concurrency=1`，随后由多个客户端使用同一 Key，或调用其他读取接口。只要角色与歌单授权允许，请求仍被接受。

影响：管理页展示的政策不等于服务端限制；不能据此承诺“单设备 Key”或并发上限。现有歌单权限检查仍然有效，此问题不意味着可读取未授权歌单。

建议：将 scopes 纳入每个接口的权限判断；确定设备登记/短租约/心跳及管理员释放协议，再接入 MusicPlayer2；以请求生命周期计数执行并发限制，并增加对应的拒绝测试。

### A2 · P1：未撤销 Key 被网页当作已撤销

定位：`server/internal/music/types.go:53`（三个时间字段），升级前 `server/internal/music/index.html:46`（`renderKeys`，本轮插入函数后约为第 47 行）。代码使用 `Boolean(k.revoked_at || k.revokedAt)` 判断撤销，最近使用也仅判断字符串是否存在。

触发：创建一个尚未撤销、尚未使用的 Key。Go `time.Time` 零值即使标注 `omitempty`，仍会序列化为 `"0001-01-01T00:00:00Z"`。该字符串为真值。

影响：新 Key 显示“已撤销”，撤销按钮被禁用；最近使用显示公元 1 年时间，无法可靠判断凭据状态。过期时间也没有用于网页状态判断。

证据强度：已使用独立标准库 Go 程序验证零值序列化结果；网页效果由上述分支直接推导，未在浏览器重现。

建议：API 在视图层省略零时间或使用可空日期；前端判定真实非零日期，并把“有效/已过期/已撤销”明确区分。

### A3 · P1：Web 的 Key 调用测试误报认证成功

定位：升级前 `server/internal/music/index.html:29`（`testKey`），`server/internal/music/server.go:49`（health 跳过认证）、`:67`；`store.go:105`（`publicAPIKey` 列表不含 secret）。

触发：在概览选择一个 Key 测试。升级前函数请求公开 `/health`，使用 `k.secret || ''`；而列表中的 Key 本就不包含完整密钥。服务器只要可达就会成功，错误、撤销、过期或空密钥不会参与该结果。

影响：管理员把“服务可达”误解为“这个 Key 可用”。建议要求输入本次测试的完整 Key，并调用受认证的 `/playlists` 或专用认证探测接口，展示认证结果与授权资源数。

此问题仅针对升级前 Web 概览。**MusicPlayer2 的 `CheckConnection` 在 `RemoteLibraryClient.cpp:134` 已请求 `/api/v1/playlists`，没有这个 health 假成功问题。**

### A4 · P1：上传成功入库后再保存元数据，失败重试可能产生重复

定位：升级前 `server/internal/music/server.go:418`（先 `ImportAudio`）、`:430`（再 `UpdateTrack`），`store.go:631`（`ImportAudio`），`index.html:45`（`uploadAll`，本轮约第 46 行）。

触发：音频复制与第一次库提交成功，第二次元数据保存失败。接口返回 500 “uploaded file but failed to save metadata”，但音频与库记录已经存在；网页将其标记失败，重试会重新导入。

影响：用户看到失败却已入库；重试会生成第二份文件/记录，因为上传文件名带时间戳，ID 基于路径，且没有内容哈希去重。这是源代码中确定存在的两次提交窗口，本轮没有对运行服务做故障注入。

建议：把文件、最终元数据与入库状态作为一个明确提交单元；实现暂存会话/确认、失败清理和幂等提交；内容哈希识别重复。仅将 JSON 换成 SQLite，不会自动消除两个独立业务提交之间的窗口。

### A5 · P2：拖拽顺序与歌单编辑不能可靠保存或合并

定位：`index.html:39`（`reorder`，行为以升级前首次读取为准）、`types.go:22`（`Playlist` 无 `sort_order`）、升级前 `store.go:443`（`Playlists` 按名称排序）、`:461`（`PutPlaylist` 整对象替换），`server.go:251`（歌单 PUT）。

触发一：拖拽卡片后刷新；升级前仅调整客户端数组，服务端没有排序字段，顺序恢复为按名称排序。即使前端单独发送 `sort_order`，没有服务端模型与持久逻辑仍不能完成该功能。系统 `library` 自身不可拖拽，但升级前仍可作为其他卡片的落点，不能等同于“系统歌单完全隔离于用户排序”。

触发二：两个页面读取同一歌单，一方新增曲目，另一方用旧对象编辑描述或批量加入；后一次完整 PUT 会覆盖前一次的成员、顺序或注释。

影响：排序丢失及无提示的数据覆盖。建议持久化用户歌单的显式位置，系统歌单固定展示；增加歌单修订号与 409 冲突，提供原子批量加入/成员调整 API。

### A6 · P2：上传预览不解析媒体，扩展名不能保证有效音频

定位：升级前 `index.html:44`（`addFiles`/`renderUploads`）、`store.go:632`（扩展名判定）、`:345`（`readTrack`）、`server_test.go:238`（使用重复字符串作为 MP3 上传数据）。

触发：将任意字节文件命名为允许的音频扩展名，或上传带实际标签/嵌入歌词的文件。前者在升级前会被接受；后者只按文件名/目录生成信息，队列显示的是文件信息和手填字段，而不是标签解析预览。

影响：无法在确认前发现损坏媒体；专辑被目录名污染，真实标签和嵌入歌词丢失。README 已承认不验证音频解码有效性，现有大上传测试也不是音频有效性验证。

建议：真实解析标签与歌词，专辑无标签时保留空值；区分解析失败、受支持容器和可解码音频；暂存预览再确认。封面与技术参数需要另行实现，不能随标签库引入一并宣称完成。

### A7 · P2：错误格式存在，错误语义仍不足以驱动客户端

定位：`server.go:50`（所有认证失败为 `AUTH_INVALID`）、`:407`（超限/损坏 multipart 均返回 400）、`:535`（单参数错误默认 `REQUEST_FAILED`）；`RemoteLibraryClient.cpp:433`（非 2xx 仅显示 HTTP 状态）；`:251`（请求失败均回退离线快照）。

触发：缺少 Key、Key 撤销或过期、无权读取、上传超过限制、元数据不合法；有离线快照时，桌面同步遭遇 401/403 也进入 offline 路径。

影响：管理员与播放器不能稳定区分重新配置凭据、授权不足、修复字段与重试网络；Key 撤销/过期可能在界面上表现为普通离线。离线读取既有缓存是初版需求，此结论不等于服务器授权被绕过，也不能保证撤销能收回已下载文件。

建议：保留内部失败原因并返回 `AUTH_MISSING`、`KEY_REVOKED`、`KEY_EXPIRED` 等稳定错误码；超限返回 413；MusicPlayer2 读取错误体并显示 message/request_id，区分认证/授权失败与网络中断，同时明确离线缓存政策。

### A8 · P2：扫描与上传持有全局锁，路径 ID 对重命名不稳定

定位：升级前 `store.go:287`（`Scan` 全程锁内遍历/读取/哈希）、`:365`（以相对路径散列生成 ID）、`:636`（`ImportAudio` 锁内复制/哈希/保存），`:156`（认证也取得写锁）。

触发：大量媒体重扫或大文件上传时其他请求进入；目录出现一个读取错误；已编辑/已加入歌单的音频被移动或重命名。

影响：其他读/认证请求可能等待昂贵 I/O；单文件失败使整次扫描中止；路径变化被当成旧曲目消失、新曲目出现，旧 ID 关联的人工覆盖、歌单成员与排除状态不能自动迁移。没有完成负载测试，不能据此给出延迟数字。

建议：锁外采集、短事务提交、后台可追踪扫描与逐文件失败报告；明确稳定曲目身份和移动检测策略。保持未变化扫描不产生无意义修订可进一步减少完整快照传输。

### A9 · P2：概览、Key 使用与任务设置仍有占位语义

定位：`index.html:11`（五个页面）、`:13`（“已连接 Key”）、`:28`（值为 `state.keys.length`）；升级前 `store.go:170`（最近使用仅内存更新）。

触发：查看概览；Key 已撤销仍留在列表；Key 仅发生访问后重启且没有其他保存操作。

影响：凭据总量被误当为在线连接数，最近使用不能稳定跨重启保存；没有扫描历史、存储统计、真实调用聚合或设置入口，无法进行设计中的运维管理。

建议：先把指标命名与真实含义对应；持久化使用时间时进行节流，统计按 Key ID/时间窗口聚合；设备在线数以租约为依据。任务和设置需新增实际模型与接口，不能只补导航标签。

### A10 · P2：存储与文档需要在升级后重新对齐

定位：升级前 `store.go:33`（JSON 加载）、`:267`（临时文件保存）、`:539`（失败回滚）；`server/README.md:3`、`:32`、`:35`、`:71`。

影响：升级前 JSON 能支持个人原型与失败回滚，但没有数据库关系约束、跨进程协调或编辑冲突协议；README 对标准库、目录专辑、JSON 及权限的陈述已与阶段发展不同步。本轮正在迁移数据库与标签，不能仅依据新增依赖确认迁移或数据兼容已完成。

建议：升级后验证旧库导入、曲目/歌单/注释/覆盖/排除/Key 保留、失败不损坏旧文件与重启结果；更新启动参数、数据文件、依赖、备份和真实能力说明。数据库事务与业务修订冲突是不同问题，应分别验收。
