# 音乐服务器管理界面与权限设计

## 结论

当前提出的左侧导航和五个业务页面适合作为正式管理端的基础。建议把管理端和播放器 API 明确分开：管理端用于管理员维护媒体库，播放器只读取被授权的歌单和曲目。这样可以让网页功能逐步变复杂，而不会把管理权限带到 MusicPlayer2 或 ESP32。

当前初版代码仍使用单个启动参数 `-api-key`、JSON 文件和整歌单替换接口。下一阶段应先完成密钥、权限和错误格式，再重做管理页；否则界面虽然能展示权限设置，服务端仍可能被直接调用绕过。

## 管理界面

左侧固定导航栏可折叠，展开时显示图标和文字，折叠时只保留图标并提供悬浮提示。桌面端保持固定宽度，窄屏时改为抽屉式导航。建议页面顺序如下：

1. **概览**：显示媒体总数、歌单数、待处理上传、最近扫描、存储占用和 API 调用情况。
2. **歌单**：管理歌单基本信息、封面、顺序和曲目。
3. **曲目**：搜索、筛选、批量编辑和批量加入歌单。
4. **上传**：拖拽文件、解析预览、人工修订和确认入库。
5. **API Key**：创建、授权歌单、撤销、过期和查看使用状态。
6. **任务/设置**：扫描任务、媒体目录、日志保留和系统参数。第一版可以先隐藏，保留接口位置。

概览页中的调用统计应按 Key ID 聚合，只显示 Key 名称或末尾标识，绝不显示完整密钥，也不保存完整 `Authorization` 请求头。音频下载量较大时应按时间窗口聚合或采样，避免每个分片都产生一条详细日志。

### 歌单页

竖向卡片列表的设计合适。每个卡片包含封面、标题、描述、曲目数、更新时间和更多菜单。拖拽排序时应只改变 `sort_order`，不要依赖名称排序。封面应作为独立资源保存，歌单 JSON 只保存 `artwork_id` 或封面 URL。

`library` 这类系统歌单应单独标记，不能删除，也不应和用户歌单混在拖拽排序中。歌单内曲目顺序和曲目注释需要独立保存，建议后续从 `TrackIDs []string` 迁移为：

```text
playlist_items
- id
- playlist_id
- track_id
- position
- note
- added_at
```

排序提交应携带 `base_revision`。如果另一位管理员已经修改歌单，服务端返回 `REVISION_CONFLICT`，前端重新加载后让用户决定合并，不能静默覆盖。

### 曲目页

“全部”和“孤立”筛选很有价值。孤立曲目的定义建议是“不属于任何用户歌单”，系统 `library` 不参与判断，否则扫描进来的每首曲目都会被认为已归属。后续可增加未解析元数据、缺少歌词、缺少封面、疑似重复等筛选。

曲目页适合提供批量加入歌单、批量编辑和批量移除库记录。删除库记录和删除原始音频文件要分成两个动作，默认只移除索引记录，避免误删用户文件。

### 上传页

上传建议采用两阶段流程：

1. 文件进入临时目录并计算内容哈希。
2. 服务端解析标签、封面、歌词、时长和技术参数，生成预览。
3. 用户修改或确认标题、艺术家、专辑、分类和歌词关联。
4. 确认后正式移动到媒体目录并写入媒体库。

上传记录可以使用 `pending`、`ready`、`accepted`、`duplicate`、`failed` 状态。重复判断以内容哈希为主，标题、艺术家和时长只作为辅助提示。人工修改过的字段应标记为锁定，重新扫描时不能覆盖。

当前服务端主要按文件名解析标题和艺术家，还没有真正读取 ID3/Vorbis/MP4 标签、嵌入封面和嵌入歌词。建议使用 TagLib 或同类库读取标签和图片，使用 `ffprobe` 补充时长、码率和采样率；外部歌词服务只能提供候选结果，最终由用户确认。

## API Key 和权限

“一个 Key 同时只能被一个请求使用”和“一个 Key 只能给一个客户端使用”是两个不同需求。前者会让播放器的同步、音频下载和歌词请求互相排队，网络稍慢时体验会明显变差；推荐实现后者，并额外提供并发上限。

建议 Key 字段如下：

```text
id
name
secret_hash
role                  admin / player / readonly / device
scopes                sync, read_track, read_media, write_library
allowed_playlist_ids  默认空数组，表示无权访问任何歌单
device_id             可选的客户端实例标识
max_devices           默认 1
max_concurrency       默认 4，可调为 1
created_at
expires_at
last_used_at
revoked_at
```

密钥只在创建时显示一次，服务端保存哈希。播放器首次配置时生成随机 `device_id` 并登记；同一个 Key 的第二个设备在已有租约未过期时返回 `DEVICE_LIMIT_REACHED`。设备掉线后通过短租约和心跳自动释放，也应提供管理员强制撤销设备的操作。并发上限用于防止异常客户端占满服务器，ESP32 可以把它配置为 1，但不能把所有 Key 都硬编码为串行。

推荐权限边界：

- `admin`：管理媒体库、上传、编辑曲目、管理歌单和 Key。
- `player`：同步和读取被授权的歌单、曲目、音频和歌词。
- `readonly`：只读指定歌单。
- `device`：专供桌面播放器或 ESP32，默认只读。

默认新 Key 的 `allowed_playlist_ids` 必须为空。只有管理员显式授权后，歌单才会出现在同步结果中。歌单权限必须在列出歌单、读取歌单详情、读取曲目和下载 `/media/{id}` 时全部检查，不能因为知道曲目 ID 就绕过权限。系统 `library` 是否开放也要单独配置。

## 统一错误格式

所有 API 错误建议使用同一结构，并返回请求 ID：

```json
{
  "error": {
    "code": "PLAYLIST_ACCESS_DENIED",
    "message": "当前密钥无权访问该歌单",
    "request_id": "req_01..."
  }
}
```

第一批稳定错误码建议包括：

```text
AUTH_MISSING
AUTH_INVALID
KEY_REVOKED
KEY_EXPIRED
DEVICE_LIMIT_REACHED
PLAYLIST_ACCESS_DENIED
TRACK_ACCESS_DENIED
TRACK_NOT_FOUND
INVALID_METADATA
UPLOAD_UNSUPPORTED
DUPLICATE_TRACK
REVISION_CONFLICT
RATE_LIMITED
SERVER_BUSY
```

HTTP 状态码仍按语义使用：401 表示没有通过认证，403 表示已认证但无权访问，404 表示资源不存在，409 表示版本或设备冲突，413 表示上传过大，429 表示限流。播放器应针对 401、403、404 分别提示，而不是全部显示为“服务器错误”。

## 存储和接口演进

JSON 文件适合当前个人单用户原型，但 Key、设备租约、请求日志、上传暂存和并发修改加入后，建议迁移到 SQLite。迁移前可以保留现有 JSON 导入功能，避免丢失已扫描的 438 首曲目和现有歌单。

建议新增或调整的接口方向：

```text
POST   /api/v1/auth/keys
GET    /api/v1/auth/keys
PATCH  /api/v1/auth/keys/{id}
DELETE /api/v1/auth/keys/{id}
POST   /api/v1/auth/keys/{id}/rotate
POST   /api/v1/auth/devices/heartbeat

GET    /api/v1/playlists?authorized=true
PATCH  /api/v1/playlists/{id}/order
POST   /api/v1/playlists/{id}/items:batchAdd

POST   /api/v1/uploads/sessions
GET    /api/v1/uploads/sessions/{id}
POST   /api/v1/uploads/sessions/{id}/commit
```

播放器同步接口应只返回当前 Key 可见的歌单和曲目。管理端接口必须要求 `admin` 角色，不能仅依赖前端隐藏按钮。

## 推荐实施顺序

1. 统一错误结构、请求 ID 和认证中间件。
2. 引入 Key 表、角色、歌单授权、撤销和过期逻辑。
3. 为曲目下载和歌词读取补充歌单权限检查。
4. 给歌单增加封面、显式排序和修订冲突保护。
5. 将 JSON 存储抽象成可迁移到 SQLite 的仓储层。
6. 重做内嵌 Web 管理页，实现左侧导航和歌单/曲目管理。
7. 增加上传暂存、媒体标签解析和确认入库。
8. 更新 MusicPlayer2 的 401、403、Key 撤销和授权歌单处理，再扩展 ESP32 客户端。

这个顺序能先封住权限绕过和数据覆盖风险，再投入管理页视觉和媒体解析，避免先做出看似完整但服务端边界不可靠的界面。
