# 开发提交与版本发布流程

生效日期：2026-10-24。适用于 MusicServer 后续开发、修复和发行；替代早期计划中一次性的推送及云端部署授权。

## 标准流程

阶段开发与验收 → Git 本地提交 → 用户显式要求推送并发布 → 推送代码和版本标签 → GitHub Actions 测试、构建、签名及发布 → 用户在云端网页检查并确认更新。

1. 每完成一个可验收阶段，执行与改动相应的验证，记录真实结果，更新计划中的完成项，再创建本地提交。只提交相关源码、文档和验证脚本；密钥、密码、数据库、媒体、归档及构建产物不入库。
2. 未收到本次明确的推送要求时，停留在本地提交。多个已验收阶段可以积累后统一发行。历史推送或部署授权不自动延续。
3. 用户要求推送并发布时，核对 `server/internal/version/version.go` 的版本号和 schema，更新 `server/deploy/release-notes.md`，完成验证和提交，确认工作区干净。新发行版本须高于已发布版本；希望云端检查出更新时，也须高于云端当前版本。同一发行版本包含多个阶段时，不必每阶段增加版本号。
4. 将待发行提交同步至 `main`，并在该提交创建、推送与代码版本完全一致的 `vX.Y.Z` 标签。发布前先核对远程状态；不得强推或覆盖已公开的标签、发行包。
5. 关注对应标签的 Actions 结果，核对正式 Release 的版本、提交、schema 和四个固定资产，再报告发布完成。流水线失败时先修复原因，不把“推送成功”等同于“发行成功”。
6. 用户在云端“系统设置 → 程序更新”点击检查更新，查看说明后确认“安装更新并重启”。日常交付无需代理通过 SSH 部署或重启服务。

## 现有 Actions 的触发规则

依据 `.github/workflows/server-release.yml`，保持现有标签发行机制：

| 操作 | 结果 |
| --- | --- |
| 推送 `main`，且改动命中服务器或工作流路径 | 运行测试，构建并签名，保存 Actions 构建产物；不发布正式 Release |
| 只推送文档等未命中路径的 `main` 改动 | 不触发该服务器工作流 |
| 推送与代码版本匹配的 `vX.Y.Z` 标签 | 运行测试、构建和签名；全部通过后上传资产并公开正式 Release |
| 手动运行工作流 | 构建所选引用；发布步骤仍要求引用为 `v*` 标签，普通分支构建不会发布 |

因此，日常所需的“推送后自动构建并发布”采用**推送代码及版本标签**。单独同步源码使用 `main` 推送，不代表发行。推送仍需用户显式要求，本规范本身不授权现在推送。

Actions 验证 Windows、Ubuntu 的 Go 测试与 vet，以及 Linux race、隔离 systemd 安装回归；然后构建 Windows/Linux amd64 固定名称程序，生成签名包，校验签名和解包结果。正式发行先以草稿上传完整资产，再公开为 latest。

固定发行资产：

- `musicserver-windows-amd64.zip`
- `musicserver-linux-amd64.tar.gz`
- `release-manifest.json`
- `release-manifest.json.sig`

签名私钥由 GitHub Actions 的 `UPDATE_SIGNING_KEY` Secret 提供，不下载到本地或云服务器。更新器读取正式 GitHub Release，不使用 Actions 临时构建产物或本地未签名包。

## 本地与 Actions 的验证分工

完整自动化回归优先由 Actions 执行，本地不默认重复运行全套测试。开发阶段按改动做必要的代码检查、针对性测试或界面验证；仅文档改动检查内容、链接和差异即可。每阶段记录实际执行范围后本地提交，尚未推送时注明 CI 待执行。

显式要求推送后，由 Actions 承担跨平台完整测试、vet、Linux race、真实 systemd 安装与回退验证，以及发行包构建、签名和校验。`package` 作业依赖 `test` 成功，测试失败不会进入正式发布；修复后须重新等待相应验证，不能绕过门禁手动发布。

Actions 不能代替所有交互验收：实际浏览器操作及特定生产环境问题仍按需要单独验证。为诊断 CI 失败而需要本地复现时，可运行相关测试；日常不为重复全套回归而额外安装本地依赖。

## 云端网页更新的能力与边界

现有 Ubuntu/systemd 更新器支持：手动检查 → 用户确认 → 自动下载 → 验证签名、大小和 SHA-256 → 停机备份 → 切换程序 → 重启 → 检查版本、提交号和 schema。启动或健康检查失败会尝试恢复旧程序及数据库快照；恢复失败时保留维护状态和诊断记录，需要排障。

定时检查只提示新版，不自动安装。安装会短暂中断服务，完成后可能需要重新登录。服务器须能访问发行仓库和下载地址，并有足够磁盘空间。

目前自动安装仅支持相同数据库 schema；跨 schema 版本需要另行设计迁移方案。网页更新只替换主程序和对应 `build.json`，不替换独立 root 更新器、systemd、Nginx、证书或其他系统配置。涉及这些组件时，在发行说明中标明，另行获得用户授权处理。

Ubuntu 安装、备份、更新及回退细节见 [部署说明](../server/deploy/README.md)。Windows 本地开发继续使用固定构建目录；云端网页自动安装能力适用于已配置独立更新器的 Linux/systemd 服务。
