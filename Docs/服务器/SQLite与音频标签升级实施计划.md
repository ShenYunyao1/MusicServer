# SQLite 与音频标签升级实施计划

日期：2026-10-07；基线：0.4.1；目标：0.5.0。

## 本轮范围

- [x] 审查服务端实际能力，对照既有后台与权限设计，记录尚未完成的功能。
- [x] 使用 SQLite 关系表保存曲目、歌单、顺序与注释、Key 与歌单授权、人工覆盖及排除记录。
- [x] 使用 SQLite-only 策略；不导入旧 JSON，`.json` 数据路径直接拒绝，新库从空快照开始。
- [x] 用真实歌曲与 MusicPlayer2 的 TagLib 实现对比作者、专辑、风格及内嵌歌词读取。
- [x] 扫描和上传读取嵌入标签；人工修改优先；同名歌词优先于嵌入歌词；空专辑不使用文件夹名。
- [x] 上传时保留嵌入标题，并将文件、人工字段和入库作为一次操作提交。
- [x] 后台显示真实专辑/风格及歌词来源；上传字段留空时自动使用音频标签。
- [x] 更新独立版本模块、README 和 update.md。

## 验收标准

1. SQLite 文件头和完整性检查正常，外键启用；邻近旧 JSON 不会被读取。
2. 重启和重扫保持 Key 哈希、授权、曲目人工编辑、歌单曲目顺序/注释及排除记录。
3. 持久化失败时内存修订号与内容回滚；上传失败清理新文件。
4. 生成的中文 ID3 和 FLAC 标签样本覆盖作者与内嵌歌词；至少一首本机真实曲目完成独立工具核对和 API 实测。
5. 不把目录名用作专辑；无标签时仍能导入，使用文件名作为标题回退。
6. 完成 Go 测试、vet、构建和前端脚本检查；在隔离数据目录完成迁移/API/重启验证后更新本机测试服务。

## 边界

本轮评估会列出设置页、上传前解析预览、封面、设备租约、并发限制和调用统计等缺口。它们不因本次迁移自动成为已实现功能。SQLite 首轮保留内存快照读取模型，在事务中持久化，以保持现有 API 和播放器兼容；大规模库的增量写入后续优化。
