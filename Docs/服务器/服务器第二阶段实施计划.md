# 服务器第二阶段实施计划

## 目标

在保留现有 MusicPlayer2 协议兼容性的前提下，完成服务端权限边界和管理端第一版骨架：

- 支持多个 API Key、角色、歌单授权、撤销和轮换。
- 新 Key 默认没有任何歌单权限。
- 统一返回错误码、错误原因和请求 ID。
- 对同步、歌单、曲目和媒体下载执行服务端权限检查。
- 管理页改为可折叠侧栏和概览、歌单、曲目、上传、Key 页面。

## 非目标

本轮不迁移 SQLite，不引入第三方媒体解析库，不改变 ESP32 协议，不实现完整的上传暂存工作流。媒体标签和嵌入封面解析保留到后续阶段。

## 文件范围

- `server/internal/music/types.go`：Key、权限和错误相关数据结构。
- `server/internal/music/store.go`：Key 持久化、创建、撤销、轮换和可见资源查询。
- `server/internal/music/server.go`：认证中间件、角色权限、结构化错误和 Key API。
- `server/internal/music/server_test.go`：权限和错误回归测试。
- `server/internal/music/index.html`：现代化管理页导航和各页面基础交互。
- `server/cmd/musicserver/main.go`：兼容现有启动参数并输出初始配置提示（如需要）。

## 实施顺序

1. 扩展数据模型并保持旧 JSON 可加载。
2. 实现 Key 生成、哈希存储、列表、撤销和轮换。
3. 实现认证上下文和角色/歌单权限检查。
4. 改造统一错误响应并增加请求 ID。
5. 为 `/sync`、`/playlists`、`/tracks`、`/media`、上传和扫描增加边界检查。
6. 更新 Web 管理页，使用现有 API 展示和操作核心数据。
7. 执行 `gofmt`、`go test ./...`、`go vet ./...` 和服务端构建；检查旧播放器使用 `-api-key` 的兼容性。

## 完成标准

- 旧的 `-api-key` 仍可作为管理员 Key 使用。
- 新建 player/device Key 后默认同步结果为空，授权歌单后才能读取对应媒体。
- 未认证、无权限、资源不存在和版本/配置错误能够通过稳定错误码区分。
- 直接请求未授权的 `/media/{id}` 返回 403。
- Web 管理页可以进入五个页面，概览和 Key 页面可读取真实数据，歌单/曲目操作保持可用。
