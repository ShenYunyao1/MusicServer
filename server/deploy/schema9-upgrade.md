# schema 8 → 9 升级与数据保留

本文件随 v0.21.18／schema 9 发行包提供。已锁定的正式 schema 8 桥接为 **v0.21.17**，提交 **37f14b957739386d3dda4d94b0e217e8fc43b1c9**；签名、归档摘要、程序身份及 8→9 能力均已验收，记录在 `schema9-bridge.json`。开发构建和分支产物不代表正式可安装版本。

## 已有 schema 8 安装

1. 保存完整备份、配置及原有受限邮件凭据。不要删除数据、重新初始化账号、改 SQLite 版本标记或重新导入曲目。
2. 先通过现有更新能力安装正式 **v0.21.17／schema 8 桥接主程序**。它识别 schema 9 清单，但仍运行 schema 8；常听导航和统计上报关闭，统计接口明确返回 `501 LISTENING_DISABLED`。当 latest 已是 schema 9，使用现有更新界面指定版本 0.21.17，或停服后手工替换已验签的桥接包，不修改库版本标记。
3. 独立更新器不会随网页主程序更新。维护者按 [更新器维护说明](updater-maintenance.md)，从固定可信公钥验签并核对大小／SHA-256 的 B 包维护 worker。仅能从同 schema 的正式 B 解包程序维护，不用 schema 9 程序直接替换 schema 8 worker，不编辑能力文件伪造支持。
4. 确认主程序与 worker 均为 B 的正式版本／提交，能力包含 schema 8、9 和明确的 8→9 边，再检查更新并由用户确认安装更高版本的 schema 9 发行 V。
5. 新程序保留原账户、密码、Key、UUID、歌单、标签和媒体路径，先保存独立 schema 8 快照，再以事务创建三张听歌统计表。健康检查核对版本、提交及 schema 9；失败恢复旧程序和 schema 8 快照，不让旧程序读取新格式数据库。

Windows 手动更新同样需要停服、备份、核验正式包；原数据目录保留。新安装直接创建 schema 9。统计只从启用后开始，不推算历史次数。

## 发行前置门禁

先正式发行 B，再将其真实 tag 和 40 位提交填写到 `deploy/schema9-bridge.json`。schema 9 的正式打包命令使用 `-formal`；Actions 下载该非草稿、非预发行 Release，核对 tag 对应提交、固定公钥签名、两个包的大小／SHA-256，以及 Linux 包中的 build 身份和 8→9 worker 能力。B 必须高于 0.21.14 且低于 V。不存在合格 B 时禁止将 V 发布为 latest。

本地隔离桥接预览使用 Go overlay 且禁用 VCS 身份，只用于旧 8→桥接 8→9 数据与功能门禁验收，不能通过正式资产校验，也不能代替真实签名发行链验收。

历史 schema 7 不在当前验收矩阵；其旧备份如需使用，应在隔离的兼容 schema 8 历史程序恢复后再走本页流程。schema 9 不接受直接 7→9 恢复，也不支持降级。
