# 独立更新器维护与 schema 7 桥接

本页对应标签系统 P01 的本地开发代码。已发布的 0.20.2 不包含新增维护命令；以下步骤须等桥接版经过 CI 并正式发行后使用。当前没有授权或执行云端维护。

## 升级顺序

现有 schema 7 的旧主程序和旧独立更新器都拒绝跨 schema 更新。平滑引导分三步：

1. 先正式发行仍使用 schema 7 的桥接版，用户通过现有网页更新主程序。桥接版会识别签名清单中的明确迁移来源，但此时仍不创建标签表或升级现有数据库。
2. 在单独授权的维护窗口，由 root 使用已验签的同 schema 桥接包更新独立更新器。该命令只替换固定位置的更新器；音乐主服务、current 链接及数据库保持。
3. 等标签表定义完成、schema 8 新版通过迁移及回退门禁后再发行。用户在桥接版网页检查更新并确认，独立更新器停服、备份、切换，主程序事务迁移，健康失败时恢复旧程序和 schema 7 快照。

只更新独立更新器并不能让旧 0.20.2 网页支持跨 schema；主程序桥接和 root 维护两步都要完成。未知 schema 或未声明支持的路径继续拒绝，不清库。

## 受控维护命令

使用正式桥接 Release 的四个固定资产。先用已知公钥验证清单签名、包大小及 SHA-256，确认对应 Linux amd64 版本；再把包安全解压到 root 拥有、组和其他用户不可写的目录。不要以 root 执行尚未验证的下载程序。不能在尚无正式桥接 Release 时把下面版本变量直接填写成 0.20.2。

在已验证的解包目录执行，`BRIDGE_VERSION` 为该包的正式版本，格式 `X.Y.Z`：

```sh
sudo ./musicserver-updater \
  -config /etc/musicserver/updater.json \
  -refresh-worker "$BRIDGE_VERSION"
```

运行中的候选程序必须有干净、已知的 VCS 身份，并与从固定官方仓库重新取得、验签和解包的目标完全匹配。它要求主程序与包的 schema 相同，禁止利用此维护入口顺便迁移数据库，拒绝降低已安装的应用／更新器版本或替换不同提交的同版本。

固定安装位置为 `/usr/local/lib/musicserver/musicserver-updater`；路径不来自网页请求。命令取得 `worker.lock`，确认没有未完成应用更新或维护标记，再以 root 权限检查候选、旧程序及目录，保留 `worker-previous`，原子替换，最后发布能力文件。下载或身份检查失败时保持旧程序；能力发布失败先恢复保守能力，再恢复旧程序。保守能力恢复失败时保留新程序并报维护错误，防止新能力与旧程序混用。

不要省略 `-refresh-worker` 来尝试更新已安装的独立程序。普通工作模式只处理队列；发布能力前会验证实际执行文件和固定安装位置的程序字节相同，解包中的未安装新版无法提前宣称能力。

## 状态与回退

`/var/lib/musicserver-update/capabilities.json` 由已安装的 root 更新器生成，应用只读；包含协议格式、程序版本／提交、支持的 schema 以及明确的 7→8 转换。读取要求文件及父目录由 root 拥有、不可由组／其他用户写入，拒绝链接或非普通文件。旧更新器没有该文件时仍可执行原有的 7→7 更新。

维护不更换 systemd 单元、Nginx、证书或应用配置，不是远程自更新 root 工具的网页入口。若有活动更新，先按既有恢复流程完成；不要删除 job、维护标记或数据库来强制继续。网络代理仍按既有 root 服务的受控环境配置，不把凭据写入命令记录或 Git。

新独立更新器可处理正常 7／8 库的完整性与双 schema 身份，安装前核验停机备份对应源程序，健康校验对应目标身份。回退使用源库快照，不让旧程序读取已迁移的新库。

P01 当前只演练 schema 8 的迁移账本；最终标签 DDL 在 P02、首次启用 schema 8 之前补齐。真实 systemd 服务安装、跨 schema 失败回退及最终发行包门禁由 Actions 执行；本地 Linux 测试不等于已完成云端维护。
